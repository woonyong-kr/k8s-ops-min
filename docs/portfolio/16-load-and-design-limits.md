# 16. 어디까지 재봤고 어디서 무너지는가

`부하 한계를 재지 않았습니다`라고 적어 두고 있었습니다. 그 상태로는 만든 것이 어느 규모까지 쓸 수 있는지 저도 모릅니다.

행 수를 늘려가며 다시 쟀습니다. 결론부터 적으면 **관측 470만 행 / 3.4GB 까지 확인했고, 그 지점에서 검사 하나가 전체 시간의 80%를 씁니다.**

---

## 1. 어디까지 쟀나

| | 1차 | 2차 | 배 |
|---|---:|---:|---:|
| `observed_fields` | 603,618 | 4,667,754 | 7.7x |
| `observed_rows` | 120,762 | 939,213 | 7.8x |
| `normalized_evidence` | 60,762 | 470,421 | 7.7x |
| 테이블 총 크기 | 313 MB | **3,463 MB** | 11x |
| 검사 8종 + 조회 2종 합계 | 150.0 ms | **2,590.3 ms** | **17.3x** |

**데이터가 7.7배 늘 때 검사 시간은 17.3배 늘었습니다. 선형이 아닙니다.**

## 2. 어느 질의가 자라나

| 질의 | 60만 행 | 470만 행 | 배 |
|---|---:|---:|---:|
| 08 중복 적재 후보 | 95.7 | **2,068.3** | 21.6x |
| 05 최신성 위반 | 29.7 | 239.6 | 8.1x |
| 90 리소스별 최신 상태 | 14.2 | 157.4 | 11.1x |
| 91 리니지 역추적 | 0.8 | 78.4 | **98x** |
| 03 스키마 드리프트 | 2.5 | 23.1 | 9.2x |
| 02 필수 필드 누락 | 4.0 | 18.9 | 4.7x |
| 01 소스 커버리지 | 0.9 | 1.3 | 1.4x |
| 04 버전 미갱신 변경 | 0.6 | 0.6 | 1.0x |
| 06 리니지 단절 | 0.6 | 1.1 | 1.8x |
| 07 실행 정합성 | 1.0 | 1.6 | 1.6x |

**넷은 데이터가 늘어도 안 자랍니다.** 01·04·06·07은 470만 행에서도 1ms 대입니다. 등록 정보와 실행 이력만 보는 질의라 관측 데이터가 늘어도 영향이 없습니다.

**08이 전체의 80%를 씁니다.** 2,590ms 중 2,068ms입니다.

**91 재귀 CTE 는 기울기가 가장 급합니다.** 절대값은 78ms 로 작지만 98배로 늘었습니다. 간선이 313개인 지금이 그렇습니다. 간선이 늘면 여기가 먼저 문제가 됩니다.

## 3. 08 은 왜 자라나

실행 계획을 봤습니다.

```
GroupAggregate  (actual time=717.687..717.688 rows=0)
  Filter: (count(DISTINCT run_id) > 1) AND (max(ingested_at) >= now() - '2 days')
  Rows Removed by Filter: 470421
  ->  Incremental Sort  (actual rows=470421)
        Sort Method: quicksort  Peak Memory: 32kB
        ->  Index Only Scan using ix_catalog_normalized_evidence_dup  (actual rows=470421)
```

**매 실행마다 470,421행을 전부 읽고 전부 버립니다.** 결과는 0행인데 스캔은 전량입니다.

디스크 정렬 문제는 아닙니다. `Peak Memory: 32kB` 로 메모리 안에서 끝납니다. 순수하게 **읽는 양이 데이터에 비례**해서 자라는 것입니다.

### 이건 실수가 아니라 감수한 것입니다

기간 조건을 `WHERE` 로 내리면 스캔이 줄어듭니다. 그런데 그러면 이 검사가 잡아야 할 사례를 놓칩니다.

```
원본     06-01 에 관측, 06-01 에 적재
복제본   06-01 에 관측, 07-30 에 적재     ← backfill 이 만든 중복

WHERE ingested_at >= 최근 2일  →  원본이 걸러져 그룹에 복제본만 남음
                                  → "1건짜리 그룹" 이라 중복으로 안 잡힘
```

**재시도와 backfill 이 만드는 중복이 정확히 이 모양입니다.** 그래서 그룹을 먼저 만들고 `HAVING` 에서 기간을 봅니다. 정확성을 위해 전체 스캔을 받아들인 것입니다.

→ 질의와 주석: [`sql/quality/08_duplicate_candidates.sql`](../../sql/quality/08_duplicate_candidates.sql)

## 4. 그래도 고칠 수 있습니다 — 재봤습니다

정확성을 지키면서 스캔을 줄이는 방법이 있습니다. **두 단계로 나누면 됩니다.**

1. 최근 적재분에서 **후보 키만** 뽑는다 (`cluster_id`, `source_id`, `resource_uid`, 날짜)
2. 그 키에 대해서만 전체 기간을 조회한다

원본이 5일 전이어도 복제본이 어제 들어왔다면 2단계에서 같은 그룹으로 묶입니다. **놓치는 사례가 없습니다.**

| | 실행 시간 |
|---|---:|
| 현재 (전체 GROUP BY) | 810 ms |
| 2단계 질의 | 673 ms |
| 2단계 + `ingested_at` 인덱스 | **460 ms** |

470만 행 중 최근 2일 적재분이 41,221행(8.8%)일 때 **1.76배** 빨라집니다. 실제 운영에서는 하루 적재분 비율이 이보다 낮으므로 효과가 더 큽니다.

**아직 적용하지 않았습니다.** 지금 질의가 검증된 상태이고 2단계 질의는 검사 결과가 같은지 더 확인해야 합니다.

## 5. 수억 행에서는 어떻게 되나

**모릅니다. 이 수치를 외삽하면 안 됩니다.**

근거를 적습니다.

**08 은 전체 스캔이라 데이터에 거의 비례합니다.** 470만 행 2.0초를 그대로 늘리면 1억 행에서 40초가 넘습니다. 그런데 그 구간에서는 `work_mem` 을 넘겨 디스크 정렬로 떨어지므로 실제로는 더 나빠집니다. 지금 측정은 메모리 안에서 끝난 값이라 **그 변곡점 이후를 예측할 수 없습니다.**

**91 재귀 CTE 는 간선 수에 따라 급격히 자랍니다.** 313개에서 78ms 이고 기울기가 98배였습니다. 깊이 제한이 없어서 간선이 순환하거나 깊어지면 어디까지 갈지 알 수 없습니다.

**측정 환경이 단일 인스턴스입니다.** 동시 실행, 다른 워크로드와의 경합, 커넥션 풀 포화는 재보지 않았습니다.

## 6. 이 규모를 넘기려면

우선순위대로 적습니다.

1. **08 을 2단계 질의로 교체** — 검증 완료(1.76배), 결과 동등성 확인 후 적용
2. **`ingested_at` 인덱스 추가** — 위와 함께
3. **관측 테이블 시간 파티셔닝** — 08·05·90 이 모두 관측 데이터 전량을 훑습니다. 월 단위로 나누면 최근 파티션만 봅니다
4. **91 에 깊이 제한** — 지금은 무제한 재귀입니다
5. **검사를 증분으로** — 마지막 검사 이후 변경분만 보는 구조. 3번과 함께 가야 의미가 있습니다

## 7. 실제로 얼마나 돌았나

부하는 못 쟀지만 **가동 이력은 남아 있습니다.** 2026년 7월 AWS 청구 원장입니다.

| 항목 | 사용량 |
|---|---|
| CloudWatch 로그 수집 | 64.354 GB |
| Classic LoadBalancer | 2,150 시간 |
| NAT Gateway | 1,274 시간 |
| 사용 중 공인 IPv4 | 8,179 시간 |
| EC2 인스턴스 (r6i.xlarge) | 1,062 시간 |

7월은 744시간입니다. **공인 IPv4 8,179시간은 약 11개가 한 달 내내 붙어 있었다는 뜻**이고, 로그 64GB 는 시연 한 번으로 나오는 양이 아닙니다.

**반복 사용자를 확보했다는 뜻은 아닙니다.** 다만 "시연 한 번 하고 껐다"와는 다릅니다.

→ 콘솔 캡처: [AWS 청구 원장 재확인](../evidence/aws-bill-2026-07/)

## 정리

| 질문 | 답 |
|---|---|
| 어디까지 재봤나 | 관측 470만 행 / 3.4GB |
| 그 지점에서 얼마나 걸리나 | 검사 8종 + 조회 2종 합계 2,590ms |
| 무엇이 먼저 무너지나 | 08 중복 적재 후보 (전체의 80%) |
| 왜 그런가 | 정확성을 위해 전체 스캔을 감수했기 때문 |
| 고칠 수 있나 | 2단계 질의로 1.76배 확인. 미적용 |
| 수억 행에서는 | 외삽 불가. 파티셔닝 없이는 안 됨 |
