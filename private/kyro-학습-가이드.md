# Kyro 카탈로그 계층 — 이해하고 방어하기

이 문서는 내부 작업 자료라는 의미로 `private/`에 분류하며 저장소에도 함께 기록합니다.

목적은 하나입니다. **면접에서 "이거 직접 하신 거 맞나요"를 들었을 때, 코드를 열지 않고 말로 설명할 수 있게 되는 것.**

읽는 순서대로 따라가면 됩니다. 각 단계 끝에 **AI에게 그대로 붙여넣을 질문**을 뒀습니다. 답을 읽고 나서 저장소의 해당 파일을 열어 보면 두 배로 빨리 붙습니다.

---

## 0. 먼저 — 이미 아는 것부터 확인하기

새로 배울 게 많아 보이지만, 절반은 이미 하신 일과 같은 생각입니다.

| 카탈로그 계층에서 하는 말 | 이미 하신 것 |
|---|---|
| 수집 완전성 3-state 계약 | `completed` / `partial` / `unavailable` + reason code |
| 부분 실패를 성공으로 덮지 않는다 | provider 하나 실패해도 나머지 evidence 는 살리고 상태를 보존 |
| 응답에 상한을 두되 잘렸다는 사실을 같이 준다 | payload 크기 제한 + truncation metadata |
| 불완전한 스냅샷을 삭제 근거로 쓰지 않는다 | inventory coverage 계산 |
| 값 대신 참조만 내보낸다 (allowlist projection) | ConfigMap · Secret 참조 API |

**이 다섯 줄이 프로젝트 전체의 철학입니다.** 카탈로그 계층은 이걸 다른 시점에 적용한 것뿐입니다.

- 하신 일 = **수집하는 순간** 무엇을 못 가져왔는지 알린다
- 카탈로그 = **수집이 끝난 뒤** 데이터가 조용히 어긋나는 걸 잡는다

면접에서 "이 프로젝트 한 줄로 설명해 보세요"를 들으면 이렇게 답하면 됩니다.

> 수집이 성공해도 데이터는 어긋납니다. 원천이 필드 타입을 바꾸거나, 같은 날짜가 두 번 적재되거나, 어제부터 아무것도 안 들어오는데 아무도 모르는 경우입니다. 그래서 "무엇이 어떻게 생겼어야 하는가"를 카탈로그에 등록해 두고 매일 실제 데이터와 대조합니다.

## 1. 카탈로그가 무엇인가 (30분)

**한 문장**: 데이터에 대한 데이터를 모아 두고, 실제 데이터가 그 기대와 맞는지 매일 대조하는 곳.

읽을 것 — `docs/metadata-catalog.md` 의 **용어 정의 표**와 **ER 다이어그램**만.

핵심 개념 넷:

| 용어 | 뜻 | 왜 필요한가 |
|---|---|---|
| **자산(asset)** | 관리 대상 데이터 한 덩어리 | "무엇을 감시하는가"의 단위 |
| **계보(lineage)** | 이 데이터가 어디서 와서 무엇을 거쳤는가 | 틀린 값이 나왔을 때 어디부터 의심할지 |
| **스키마 드리프트** | 원천의 모양이 예고 없이 바뀐 것 | 실패 없이 조용히 틀려지는 대표 경로 |
| **멱등(idempotent)** | 몇 번 돌려도 결과가 같은 것 | 재시도·backfill 이 데이터를 부풀리지 않게 |

> 게임 "리니지"와 무관합니다. lineage = 혈통·계보. 문서에서는 "데이터 계보"로 씁니다.

**AI에게 물어볼 것**

```
데이터 카탈로그와 데이터 리니지가 무엇인지, 실무에서 어떤 문제를 푸는지
비유를 들어 설명해줘. 그리고 "스키마 드리프트"가 왜 배치 실패보다
위험한지 구체적 사고 시나리오로 알려줘.
```

## 2. 이 프로젝트에서 가장 중요한 설계 판단 두 개 (1시간)

### 2-1. 등록 계약과 관측 이력을 나눈 이유

읽을 것 — `docs/metadata-catalog.md` 의 "계약 이력이 없으면 …" 절.

- `asset_fields` = **지금 등록된 계약**. `ON CONFLICT DO UPDATE` 로 갱신됩니다
- `schema_observations` = **관측될 때마다 한 줄씩 쌓이는 이력**. append-only

**왜 둘로 나눴나**: `asset_fields` 는 upsert 라서 이전 세대 해시가 제자리에서 덮입니다. 그러면 "버전은 그대로인데 모양이 바뀐 변경"을 판정할 기준점 자체가 사라집니다. 이력이 따로 있어야 "같은 `schema_version` 에 해시가 둘 이상"이라는 조건을 쓸 수 있습니다.

**면접 질문 형태**: "테이블을 왜 그렇게 나눴나요?"
**답의 뼈대**: 갱신되는 것과 쌓이는 것을 한 테이블에 두면, 갱신이 과거를 지워서 비교 대상이 없어집니다.

### 2-2. 실행 단위를 두 계층으로 나눈 이유

- `catalog_dag_runs` = 배치 실행 하나 (`SUCCESS` / `PARTIAL` / `FAILED` / `INCOMPLETE`)
- `catalog_collection_runs` = 원천 하나의 수집 (`SUCCESS` / `NO_DATA` / `TRUNCATED` / `FAILED`)

**왜**: 배치 하나에 행이 하나면 원천이 넷일 때 어느 원천이 실패했는지 적을 자리가 없습니다. `PARTIAL` 은 "여러 원천을 가진 실행"의 성질이라 `dag_runs` 에만 존재합니다.

**여기서 반드시 알아야 할 것**: `NO_DATA` 와 `FAILED` 를 합치면 안 됩니다. "없는 것"과 "못 가져온 것"이 같아지면 매일 전량을 다시 수집하게 됩니다. **이건 하신 3-state 계약과 정확히 같은 논리입니다.**

**AI에게 물어볼 것**

```
SQL에서 upsert(ON CONFLICT DO UPDATE)를 쓰는 테이블과 append-only 이력
테이블을 분리하는 설계 패턴을 설명해줘. 왜 한 테이블에 둘 다 담으면
"과거와 비교"가 불가능해지는지 예시로 보여줘.
```

## 3. SQL — 반드시 넘어야 할 세 본 (3~4시간, 가장 중요)

면접에서 SQL을 파고들면 이 셋 중 하나가 나옵니다. **주석까지 읽고 "왜 이 모양인가"를 말로 설명할 수 있으면 이 파트는 끝납니다.**

### 3-1. `sql/lookups/lineage_trace.sql` — 재귀 CTE

**하는 일**: 자산 하나에서 출발해 상류·하류로 계보를 따라갑니다.

알아야 할 문법 셋:

- `WITH RECURSIVE` — 자기 자신을 참조하는 CTE. 그래프 탐색에 씀
- `depth < 10` — 순환이 있으면 무한히 돌기 때문에 깊이로 끊음
- `DISTINCT ON (…) … ORDER BY …` — PostgreSQL 전용. 그룹마다 첫 행 하나만 남김

**가장 나올 만한 질문**: "`DISTINCT ON` 에서 어떤 행이 남나요?"
**답**: `ORDER BY` 순서대로 정렬한 뒤 그룹의 **첫 행**입니다. 그래서 `ORDER BY` 를 안 정하면 어떤 행이 남을지 비결정적이 됩니다. 여기서는 확인 시각이 최신인 간선을 남깁니다.

### 3-2. `sql/checks/duplicate_candidates.sql` — 2단계 질의

**하는 일**: 같은 대상을 서로 다른 실행이 다시 적재한 경우를 찾습니다.

**이 질의의 역사가 곧 답입니다.** 세 단계로 외우세요.

1. **처음엔 아무것도 못 잡았습니다.** `(cluster_id, source_id, resource_uid, observed_at)` 로 묶고 `COUNT(*) > 1` 을 봤는데, 그 네 컬럼이 이미 유일 제약입니다. **DB가 이미 막는 걸 검사가 다시 세고 있었습니다.** 어떤 데이터에서도 0행이었습니다.
2. **그래서 시각을 날짜로 뭉갰습니다.** 유일 제약이 못 막는 중복은 `observed_at` 이 몇 초 어긋난 재관측입니다. 재시도나 backfill 이 원천 타임스탬프를 다시 계산하면 정확히 그 모양이 됩니다.
3. **그런데 느렸습니다.** 기간 조건을 `WHERE` 로 내리면 "원본은 5일 전, 복제본만 어제" 인 쌍에서 원본이 먼저 걸러져 1건짜리 그룹으로 보입니다. 잡아야 할 걸 놓칩니다. `HAVING` 에만 두면 매번 전량을 읽습니다. 그래서 **최근 적재분에서 후보 키만 먼저 뽑고, 그 키에 대해서만 전체 기간을 조회**합니다.

**반드시 같이 말해야 하는 것 (이걸 빼면 과장이 됩니다)**:

> 1.76배 빨라진 대신 내준 게 있습니다. 후보를 "최근 2일 안에 적재된 것"으로 좁히므로, 원본과 복제본이 **둘 다** 그보다 오래전에 적재된 중복은 못 잡습니다. 매일 돌리는 한 문제가 안 되지만, 배치가 이틀 넘게 멈췄다 재개되면 창을 넓혀 한 번 돌려야 합니다. 이 사각지대는 테스트로 고정해 뒀습니다.

**면접에서 이게 왜 강한가**: 최적화를 자랑하는 사람은 많지만 **무엇을 내줬는지 아는 사람은 드뭅니다.**

### 3-3. `sql/checks/source_coverage.sql` — 윈도 함수와 분기 순서

**하는 일**: 등록된 원천과 실제 실행을 대조해 다섯 가지 상태를 판정합니다.

알아야 할 것 셋:

- **`LEFT JOIN` 이고 기간 조건이 `ON` 절에 있습니다.** `WHERE` 에 두면 실행 0건인 원천이 조인 후 필터에서 탈락해, "침묵하는 원천"과 "존재하지 않는 원천"이 같은 부재로 뭉개집니다
- **`COUNT(*) FILTER (WHERE …)`** — 한 번 스캔하면서 조건별로 따로 셉니다
- **`CASE` 분기 순서가 결과를 바꿉니다.** `CHRONICALLY_TRUNCATED` 를 `DEGRADED` 보다 **먼저** 봐야 합니다. `TRUNCATED` 는 healthy 에 안 들어가므로 잘림이 절반을 넘으면 healthy 비율은 반드시 0.8 아래입니다. 순서를 반대로 두면 `DEGRADED` 가 항상 먼저 잡아서 `CHRONICALLY_TRUNCATED` 는 **어떤 입력에서도 나오지 않습니다**

**이게 실제로 있었던 버그입니다.** 질의를 읽어서는 못 잡았고, 판정마다 그 판정이 나오는 입력을 만들어 보고 잡았습니다.

**AI에게 물어볼 것 (셋을 따로 물어보세요)**

```
PostgreSQL의 WITH RECURSIVE와 DISTINCT ON을 예제로 설명해줘.
DISTINCT ON에서 ORDER BY를 지정하지 않으면 어떤 문제가 생기는지도.
```

```
SQL에서 LEFT JOIN의 기간 조건을 ON 절에 두는 것과 WHERE 절에 두는 것의
차이를 결과 예시로 보여줘. 왜 WHERE에 두면 LEFT JOIN이 INNER JOIN처럼
동작하는지 설명해줘.
```

```
COUNT(*) FILTER (WHERE ...)와 CASE WHEN의 조합에서 분기 순서 때문에
도달 불가능한 분기(dead branch)가 생기는 사례를 만들어서 보여줘.
```

## 4. 배치 파이프라인 (1시간)

읽을 것 — `docs/airflow-pipeline.md`

핵심 셋만:

**① 원천별 독립 수집.** 하나가 실패해도 나머지는 진행합니다. 실패를 성공으로 덮지 않고 `PARTIAL` 로 남깁니다.

**② 멱등 재실행.** 같은 논리 날짜를 다섯 번 돌려도 적재 행 수가 변하지 않습니다. 유일 제약 11종이 이걸 보장합니다.

**③ backfill 은 보관 원본에서 재생합니다.** 과거 날짜를 다시 돌릴 때 원천을 재조회하면 원천은 과거 상태를 갖고 있지 않으므로, 현재 값에 과거 날짜 도장을 찍게 됩니다.

**정직하게 말해야 하는 한계**: Airflow **스케줄러 위에서 실패 시나리오를 실제로 돌려 본 것은 자동 검증에 없습니다.** 파이프라인 함수와 질의까지가 테스트 범위입니다. 이건 `README.md` 의 한계 절과 `docs/airflow-pipeline.md` 의 완료 조건에 적혀 있습니다.

**AI에게 물어볼 것**

```
Airflow에서 catchup, logical_date, TriggerRule.ALL_DONE, mapped task가
각각 무엇인지 설명해줘. 그리고 배치 파이프라인에서 "멱등성"을 보장하는
방법(유일 제약 + ON CONFLICT)을 SQL 예제로 보여줘.
```

## 5. 조회 API 와 MCP (1시간)

읽을 것 — `docs/catalog-api-mcp.md` 의 **검증표**와 **구현하지 않은 것** 표.

**① 모든 응답이 같은 봉투를 씁니다** — `data` / `page` / `evidence`.
`evidence.run_status` 가 `PARTIAL` 이면 **이 조회 결과 자체가 부분 데이터**라는 뜻입니다. "이슈 0건"이라고 답해도 그 검사가 일부 원천을 못 봤다면 0건의 의미가 다릅니다.

**② MCP 는 모델이 도구를 부르는 표준 프로토콜입니다.** stdio 로 JSON-RPC 를 주고받습니다. 여기서는 읽기 전용 도구 7종만 노출합니다.

**③ RFC 8693 토큰 교환** — 사용자 토큰을 그대로 넘기지 않고, 카탈로그 읽기 권한만 남긴 토큰으로 바꿔서 씁니다. 교환 결과가 요청보다 넓으면 거부합니다(대상 불일치 / 범위 확대 / 수명 초과).

**정직하게 말해야 하는 한계**: MCP 는 **가짜 인증 서버와 가짜 전송으로만 검증**했습니다. 실제 STS 나 MCP 클라이언트에 붙여 본 적이 없습니다.

**AI에게 물어볼 것**

```
MCP(Model Context Protocol)가 무엇이고 stdio JSON-RPC로 어떻게 동작하는지
initialize / tools/list / tools/call 흐름으로 설명해줘.
그리고 RFC 8693 token exchange가 왜 필요한지, audience와 scope를
좁히는 게 무엇을 막는지 알려줘.
```

## 6. 테스트를 어떻게 봐야 하나 (30분)

카탈로그 계층 테스트는 **124종**입니다. 개수가 중요한 게 아니라 **성격**이 중요합니다.

| 성격 | 무엇 | 왜 있는가 |
|---|---|---|
| 회귀 차단 | 실제로 잡았던 버그가 뒤에 있음 | 같은 결함이 다시 들어오는 걸 막음 |
| 분기 도달성 | 판정마다 그 판정이 나오는 입력을 만듦 | 죽은 분기를 찾음 |
| 문서·코드 대조 | 문서의 숫자를 코드에서 세어 비교 | 문서가 코드보다 뒤처지는 걸 막음 |

**기준 한 줄**: 이 테스트가 깨졌을 때 **무엇이 잘못된 건지 한 문장으로 말할 수 있는가.** 못 하면 지울 후보입니다.

**음성 fixture 가 왜 중요한가**: 정상 데이터로만 시험하면 **"무엇이든 통과한다고 답하는 검사"도 통과합니다.** 그래서 일부러 고장 내는 명령(`make demo-fail-source` `make demo-drift` `make demo-duplicate`)을 함께 뒀습니다.

## 7. 직접 돌려 보기 (30분) — 이걸 해야 진짜 붙습니다

```bash
make catalog-up        # PostgreSQL · MinIO · Airflow 기동
make catalog-run       # 배치 1회 실행
make catalog-verify    # 15항목      → 15/15 통과
make catalog-test      # 테스트       → 124 passed
make catalog-sql       # 검사 SQL 결과 출력
make demo-drift        # 일부러 스키마를 바꿔 검출되는지 확인
```

`make catalog-sql` 출력을 보면 검사 8종이 각각 무엇을 반환하는지 눈으로 보입니다. `make demo-drift` 를 돌린 뒤 다시 `catalog-sql` 을 돌려 보세요. **"위반 없음"이 "위반 N건"으로 바뀌는 걸 직접 보는 게 문서 열 장보다 낫습니다.**

## 8. 면접 예상 질문과 답의 뼈대

**Q. 60만 행에서 잰 수치를 수억 행에 그대로 쓸 수 있나요?**
> 못 씁니다. 470만 행까지 재봤고 그 지점에서 어느 질의가 먼저 무너지는지까지 봤습니다. 원인은 SQL 품질이 아니라 **어느 테이블을 읽느냐**였습니다. 관측 이력을 읽는 검사만 자라고 등록 정보를 읽는 검사는 안 자랍니다. 수억 행은 외삽할 수 없습니다.

**Q. 검사 SQL 하나 골라서 왜 그 모양인지 설명해 보세요.**
> 3장의 셋 중 하나를 고르세요. **중복 적재 검사가 가장 강합니다** — 못 잡던 것을 발견한 이야기 + 최적화의 대가까지 있어서.

**Q. 왜 OpenMetadata 같은 걸 안 썼나요?**
> 자산이 6종이고 소유자가 한 팀입니다. 제품이 주는 것(검색 UI, 조직 통합, 플러그인)이 이 규모에서는 운영 비용을 넘지 못한다고 봤습니다. 필요한 건 **대조 기준**이었고 그건 테이블 몇 개로 됩니다. 다만 설치해 보고 판단한 게 아니라 문서를 보고 판단한 것이라 그렇게 적어 뒀습니다.

**Q. 실제로 운영해 본 건가요?**
> 아니요. 반복 사용한 사용자가 없습니다. 시연에 성공한 것과 쓰인 것은 다릅니다. 다만 7월 AWS 청구서에 로그 64.35GB, LoadBalancer 2,150시간이 남아 한 달 가까이 가동된 것은 확인됩니다.

**Q. 팀 프로젝트인데 어디까지가 본인 건가요?**
> `docs/source-and-ownership.md` 에 파일별로 정리돼 있습니다. 배치와 카탈로그 계층은 프로젝트 종료 후 개인 작업입니다.
