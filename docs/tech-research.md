# 기술 리서치 — Modern Data Stack 선택 근거

> **⑤⑥ 도구 선택 근거** · 지원 준비용 후속 확장

도구 비교표만 쓰면 아무것도 결정되지 않습니다. 요구 조건을 먼저 고정해야 비교가 의미를 갖는다.

---

## 1. 오케스트레이터

### 요구 조건 먼저

도구를 비교하기 전에 이 배치가 반드시 해야 하는 일을 적었다.

| 조건 | 필요한 이유 |
|---|---|
| 소스별 독립 재시도 | Loki 하나가 죽었다고 성공한 세 소스를 다시 긁을 수 없다 |
| 과거 구간 재처리 | 정규화 로직이 바뀌면 지난 30일을 다시 만들어야 한다 |
| 실행 이력 장기 보존 | "언제부터 어긋났나"를 나중에 물을 수 있어야 한다 |
| 실패 task만 재실행 | 전체 재실행은 원천에 불필요한 부하를 준다 |
| 로컬 재현 | 심사자가 클라우드 없이 돌려볼 수 있어야 한다 |

**세 번째와 네 번째가 기존 스케줄러를 탈락시켰다.** 제품에 이미 있던 스케줄러는 "다음 실행 시각"만 관리하고 논리 날짜 개념이 없었습니다.

### 비교

| | Airflow | Prefect | Dagster |
|---|---|---|---|
| backfill | 일급 개념. 논리 날짜로 과거 구간 재실행 | 지원하나 별도 배선 필요 | partition 기반. 개념은 우수 |
| 부분 실패 재실행 | task 단위 clear 후 재실행 | 지원 | 지원 |
| 데이터 자산 모델 | 없음. DAG 중심 | 없음 | **일급 지원.** asset 중심 |
| 실행 이력 | 메타데이터 DB에 장기 보존 | Cloud 의존도 높음 | 지원 |
| 로컬 실행 | `docker compose` 한 번 | 간단 | 간단 |
| 학습 자료 | 압도적으로 많음 | 중간 | 적음 |
| 운영 복잡성 | scheduler·worker·메타DB 필요 | 상대적으로 가벼움 | 중간 |

### 선택과 그 이유

**Airflow를 선택했습니다.** 결정적 조건은 backfill이었습니다.

Dagster가 더 맞을 수도 있었다. 이 프로젝트는 데이터 **자산**을 다루고, Dagster는 자산을 일급으로 모델링합니다. 개념적 적합성만 보면 Dagster가 낫습니다.

그럼에도 Airflow를 택한 이유는 두 가지다.

**학습 자료의 양.** 막혔을 때 답을 찾는 속도가 실제 개발 속도를 결정했습니다. 22주 과정 중 남은 시간에 새 개념 체계까지 익히는 것은 위험이 컸습니다.

**자산 모델은 이미 직접 만들었다.** Dagster의 asset 개념은 [카탈로그 스키마](metadata-catalog.md)로 직접 구현했습니다. Dagster를 쓰면 자산 정의가 오케스트레이터에 종속되는데, 카탈로그는 Airflow 없이도 조회돼야 합니다.

### 안 쓴 것

**Kubernetes CronJob.** 단일 일일 작업이었다면 이걸로 충분했습니다. backfill 요구가 생기면서 탈락했습니다. 조건이 세 개 이하로 줄면 다시 CronJob이 맞습니다.

**제품 내장 스케줄러 확장.** 실시간 수집 경로와 배치가 같은 스케줄러를 공유하면, 배치가 밀릴 때 실시간 수집이 영향을 받습니다. [관련 문서](airflow-pipeline.md)에 상세.

## 2. 데이터 카탈로그

### 후보

| | OpenMetadata | DataHub | 직접 구현 |
|---|---|---|---|
| 자산 수집 | PostgreSQL·Airflow 자동 수집 | 광범위한 커넥터 | 직접 작성 |
| 리니지 | 자동 추론 + 수동 | 자동 추론 | 직접 기록 |
| 품질 검사 | 내장 | 별도 연동 | 직접 구현 |
| 운영 부담 | Elasticsearch·MySQL·서버 | Kafka·Elasticsearch·GMS | PostgreSQL만 |
| 커스텀 검사 | 플러그인 | 플러그인 | 자유 |

### 직접 구현을 선택했다

**자산이 6종입니다.** Kubernetes 스냅샷, Prometheus 시계열, Loki 로그 스트림, Tempo 추적, 정규화 근거, 품질 보고. 이 규모에서 Elasticsearch와 Kafka를 세우는 것은 운영 비용이 이득을 넘습니다.

**검사가 이 도메인 고유하다.** 필요한 검사는 "일부 소스가 실패했는데 실행이 성공으로 기록됐는가", "잘린 스냅샷이 완전한 것으로 표시됐는가"다. 범용 카탈로그의 내장 검사에 이런 항목이 없습니다. 결국 플러그인으로 직접 짜야 합니다.

**도구 설치는 경험이 아닙니다.** OpenMetadata를 띄우고 커넥터를 붙이면 화면은 나옵니다. 그런데 드리프트가 왜 잡히는지, 리니지가 어떻게 추론되는지는 모른 채로 남습니다. 스키마를 직접 설계하면 그 판단이 전부 내 것이 됩니다.

**언제 바꿔야 하나.** 자산이 수백 개를 넘고 여러 팀이 소유자를 나눠 가지면 직접 구현의 이득이 사라집니다. 그때는 검색·권한·UI를 직접 만드는 비용이 도입 비용보다 커진다. 지금 만든 스키마는 그 이관을 염두에 두고 `qualified_name`을 유일 키로 두었습니다.

## 3. 원본 저장

| 후보 | 판단 |
|---|---|
| PostgreSQL에 JSONB | 질의는 편하나 원본이 커지면 DB가 감당하지 못합니다. 백업·복구 비용이 함께 커진다 |
| **S3 (로컬 MinIO)** | 목표 구조. 현재 pipeline은 로컬 파일만 사용하며 MinIO는 연결되지 않음 |
| 파일시스템 | 로컬 재현은 쉬우나 배포 환경에서 노드 종속이 생긴다 |

원본은 **자주 읽지 않지만 반드시 남아야 하는 데이터**입니다. 정규화 로직이 바뀌었을 때만 읽습니다. 접근 빈도가 낮고 크기가 크며 불변인 데이터는 객체 저장소가 맞습니다.

`raw_snapshots` 테이블에는 `s3_uri`와 `content_hash`를 두었습니다. 현재 `s3_uri` 값은 `file://...`이고 실제 객체 저장소 client는 없습니다. 정규화 행에서 로컬 원본까지 [리니지](sql-quality-checks.md#91-리니지-역추적)로 역추적하는 모델만 구현돼 있습니다.

`docker-compose.catalog.yml`에 MinIO 서비스가 정의돼 있지만 pipeline이 이를 호출하지 않습니다. 따라서 “MinIO로 전체 파이프라인을 재현했다”고 쓰지 않습니다.

## 4. LLM 연동 범위

### 무엇을 모델에 맡기지 않았나

카탈로그에 LLM을 붙이는 방법은 여러 가지다.

| 방식 | 판단 |
|---|---|
| 자연어 → SQL 생성 | **기각.** 생성된 질의가 맞는지 검증할 방법이 없습니다. 잘못된 집계가 그럴듯한 답으로 나온다 |
| 스키마 문서 자동 생성 | **기각.** 필드 의미를 모델이 추측하면 카탈로그의 신뢰도가 무너진다 |
| 품질 이슈 원인 추론 | **보류.** 유용하나 평가 기준이 없다 |
| **기존 API 조회 어댑터** | **선택.** 답은 결정론적 질의가 만들고 모델은 질문을 도구로 옮긴다 |

원칙은 하나다. **수치와 판정은 결정론적 코드가 만들고, 모델은 질문을 도구 호출로 옮기는 일만 합니다.**

이 경계는 [수집 완전성 계약](collection-contract.md)에서 배운 것과 같습니다. 답이 나왔다는 것과 그 답을 믿을 수 있다는 것은 다른 문제입니다.

구현은 [관련 문서](catalog-api-mcp.md)에 있습니다.

### 이전 프로젝트에서 가져온 것

협업 서비스(W15–16)에서 GitHub 저장소 질의응답을 만들었다. 거기서 두 가지를 배웠다.

**근거 범위를 고정해야 합니다.** 검색 범위를 저장소·브랜치·커밋으로 묶지 않으면 다른 버전의 코드가 한 답변에 섞인다. 카탈로그에서는 조회 결과에 `run_id`를 동봉하는 것으로 같은 문제를 다뤘습니다.

**근거가 없으면 답하지 않아야 합니다.** 검색 결과가 비었을 때 모델이 추측하면 가장 위험한 답이 나옵니다. 카탈로그 API가 `NEVER_RUN`과 `이슈 0건`을 구분하는 이유가 이것입니다.

## 이 작업이 증명하는 것

- 도구를 비교표가 아니라 **요구 조건 기준으로 평가**하고 근거를 남기는 방법
- 더 적합해 보이는 도구를 **탈락시킨 이유까지 기록**하는 태도
- 도입하지 않기로 한 결정과 **언제 다시 검토해야 하는지**를 함께 기술
- 모델이 판단할 영역과 결정론적 코드가 판단할 영역을 **나누는 기준**

## 5. 다음에 조사할 것

| 주제 | 왜 |
|---|---|
| dbt | 정규화 단계를 SQL 모델로 옮기면 검사와 변환의 경계가 명확해질 수 있다 |
| Great Expectations | 검사 정의를 코드 밖으로 빼면 비개발자도 검사를 추가할 수 있다 |
| Iceberg | 원본 스냅샷에 스키마 진화와 시점 조회가 필요해지면 |
| OpenLineage | 리니지를 직접 기록하는 대신 표준 규격으로 수집하면 도구 이관이 쉬워진다 |

지금 도입하지 않는 이유는 같습니다. **해결하려는 문제가 아직 생기지 않았습니다.**
