## 1. 가짜 데이터를 먼저 제품 경로에서 뺐다

**06-29** `chore: fake telemetry 제거 / manifest 정리 / 운영 기준`

수집기를 붙이기 전 화면 개발용으로 가짜 telemetry를 넣어 두었습니다. Prometheus 연동이 동작하기 시작한 날 이걸 먼저 지웠다.

가짜 데이터가 남아 있으면 **수집이 실패해도 화면이 정상으로 보입니다.** 실패를 실패로 보이게 만드는 것이 이후 모든 작업의 전제였습니다.

**07-06** `fix: 원시 텔레메트리 / payload 제거 / 계약 정리`

loki·prometheus·tempo에서 원본 payload 필드를 제거했습니다. 5줄 삭제다.

디버깅에 편해서 원본을 그대로 실어 보내고 있었다. 그런데 이 응답은 화면과 원인 판정으로 갑니다. **디버깅 편의가 계약에 새어 들어간 것**이라 판단해 제품 경로에서 뺐다.

이 결정에는 뒷맛이 남았다. 계약에서 뺐을 뿐 **이미 저장된 데이터는 정리하지 않았습니다.** [설정 참조 API 문서](config-reference-api.md#값은-여전히-저장돼-있다)에 그 상태를 적어 뒀다.

## 2. 한도를 네 번 조인 새벽

**07-11 04:28 → 06:01**, 1시간 33분 동안 네 커밋.

payload가 한도를 넘기기 시작했습니다. 처음엔 터진 곳만 막았다.

| 시각 | 커밋 | 무엇을 했나 |
|---|---|---|
| 04:28 | `fix: bound metadata evidence` | endpoint slices·service selectors·workload snapshots에 **각각** 한도 추가 |
| 05:27 | `fix: bound evidence payload` | **[`collection_limits.py`](../src/services/target/cluster-agent/providers/collection_limits.py) 신규.** kubernetes·prometheus provider에 적용 |
| 05:39 | `fix: harden evidence payload` | 한도 강화 + 테스트 3파일 |
| 06:01 | `fix: bound loki and tempo` | loki·tempo까지 확대 + 테스트 |

**04:28에서 05:27 사이가 이 프로젝트에서 가장 중요한 한 시간입니다.**

04:28 커밋은 provider 세 곳에 같은 로직을 각각 넣었다. 네 번째 provider를 열었을 때 같은 코드를 또 쓰고 있다는 걸 알아차렸다. 거기서 멈추고 공통 모듈로 뽑았다.

뽑고 나서 순서가 바뀌었다. 그 전에는 `provider 수정 → 다음 provider 수정`이었는데, 그 후로는 `공통 모듈 수정 → 테스트로 고정 → 나머지 provider에 적용`이 됐습니다. 05:39와 06:01 커밋에 테스트가 크게 붙은 이유입니다.

각 커밋마다 `provider-evidence-field-guide.md`와 `target-cluster-agent.md`를 함께 고쳤다. **계약이 바뀌면 문서도 같은 커밋에서 바뀌어야** 다음 사람이 코드와 문서 중 뭘 믿을지 고민하지 않습니다.

→ 결과: [수집 한도 설계](collection-limits.md)

## 3. 되돌린 커밋

**07-10 05:46** `revert: 이전 변경 / 상태 복원`

한 시간 전 커밋(`docs: document metadata provider`)을 되돌렸다. 문서 3개에서 245줄이 사라지고 43줄이 남았다.

metadata provider를 확장하면서 문서에 필드 설명을 대량으로 추가했습니다. 그런데 그 시점에 필드 구조가 아직 흔들리고 있었다. **확정되지 않은 구조를 문서로 못 박으면, 코드가 바뀔 때마다 문서가 거짓이 됩니다.**

되돌리고 구조가 안정된 뒤 다시 썼다. 같은 날 오후 커밋들(`refactor: centralize kubernetes metadata`, `refactor: split metadata provider`)이 그 안정화 작업입니다.

## 4. 리뷰 40분 뒤

**07-23 15:02** `feat: 구성 참조 read API 추가`
**07-23 15:42** `fix: 구성 참조 projection 경계값 보강`

40분 사이에 무엇이 추가됐나.

| 추가 | 이유 |
|---|---|
| 참조 수 상한 | 워크로드 하나가 수백 개를 참조하면 응답이 밀린다 |
| 신뢰할 수 없는 문자열 길이 제한 | manifest의 임의 문자열이 그대로 응답에 실린다 |
| 사유 코드 개수 상한 | 사유가 쌓이면 그것대로 응답을 차지한다 |

최초 구현에도 테스트가 적지 않았습니다. **기능은 전부 검증했는데 경계가 비어 있었다.** 리뷰에서 그 지적을 받았다.

이후 작업 순서가 바뀌었습니다. 기능 테스트를 쓰고 나서 "이 입력이 비정상적으로 크면?"을 먼저 묻게 됐습니다.

## 5. 프로젝트 이후 — 카나리 테스트

최종 프로젝트가 끝나고 설정 참조 API를 다시 봤을 때, 검증 방식이 틀렸다는 걸 알았다.

테스트는 "Secret 값이 응답에 없다"를 확인하고 있었다. **그건 내가 생각한 경로에서 새지 않는다는 뜻이지, 새는 경로가 없다는 뜻이 아닙니다.**

방식을 바꿨다. 원본 스냅샷의 모든 문자열 자리에 고유 토큰을 심고, 응답을 직렬화해서 허용 경로 밖의 토큰이 하나라도 나오면 실패시킨다.

붙이자마자 `metadata.annotations`의 `last-applied-configuration`이 걸렸다. **이전 manifest 전체가 평문 env를 포함한 채로 그 안에 들어 있었다.** 열거로는 절대 찾지 못했을 경로다.

여기서 projection 자체를 denylist에서 allowlist로 바꿨다. 지울 것을 열거하는 대신 채울 것만 채우는 방식입니다.

→ 결과: [설정 참조 조회 API](config-reference-api.md#지우는-대신-새로-만듭니다)

## 이 작업이 증명하는 것

- 같은 코드가 반복될 때 **멈추고 공통화하는 판단**
- 확정되지 않은 구조를 문서화한 것을 **되돌리는 결정**
- 코드 리뷰 지적을 받고 **작업 순서 자체를 바꾼** 경험
- 커밋 이력의 신뢰도 한계를 **스스로 밝히는** 태도

## 7. 커밋 이력을 어떻게 읽어야 하나

이 저장소는 팀 작업 중 이력 정리를 여러 번 거쳤다. 커밋 메시지에 `이력 정합성` 접미사가 붙은 커밋이 팀 전체에 다수 있고, 일부 구간에는 rebase로 생긴 중복 커밋이 남아 있습니다.

그래서 **커밋 수는 기여의 근거가 아닙니다.** 위에서 인용한 것은 판단이 바뀐 지점의 변경 내용이지 커밋 개수가 아닙니다.

기여 범위는 파일 단위 blame과 코드 자체로 확인하는 편이 정확합니다. 담당 범위는 [README](../README.md#1-이-계층이-푸는-문제)에 있습니다.

## 8. 프로젝트가 끝난 뒤

최종 프로젝트가 끝나고 남은 구멍이 하나 있었다. 수집하는 순간의 완전성은 다뤘는데 **수집이 성공한 뒤**를 못 봤다는 것입니다.

그래서 붙인 것이 [카탈로그](metadata-catalog.md)와 [배치 파이프라인](airflow-pipeline.md)입니다. 팀 프로젝트가 아니라 개인 작업이고, 기존 수집 API를 입력으로만 사용합니다.

수집기를 다시 만들지 않은 이유는 [리서치](tech-research.md)에 있습니다. 이미 도는 것을 다시 만드는 대신, 그것이 만든 데이터를 검증하는 계층을 얹는 편이 배울 게 많다고 봤습니다.

이 확장이 순수한 호기심에서 나온 것이냐고 물으면 **아닙니다.** Airflow 와 카탈로그를 우선순위 위로 올린 데에는 외부 요인이 있었습니다. 다만 고칠 대상 자체는 프로젝트 회고에 이미 적어 뒀던 것입니다. 순서가 바뀌었을 뿐 목록이 새로 생기지는 않았습니다.
