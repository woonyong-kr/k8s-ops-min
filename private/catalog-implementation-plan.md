# 카탈로그 구현 계획과 진행 상태

팀 프로젝트는 **수집하는 순간**의 완전성만 다뤘습니다. 수집이 성공한 뒤가 비어 있었습니다. 그 공백을 메우려고 종료 후 개인 작업으로 세운 계획과, 지금 어디까지 왔는지를 적었습니다.

각 항목은 **완료 / 부분 / 계획** 셋 중 하나입니다. 완료로 적은 것은 로컬에서 명령 한 줄로 재현됩니다.

---

## 1. 메타데이터 저장소

| 항목 | 상태 | 확인 |
|---|---|---|
| 자산·소스·필드 계약 테이블 | 완료 | `make catalog-schema` |
| 스키마 관측 이력 (append-only) | 완료 | `make demo-drift` |
| 리니지 간선과 확인 시각 | 완료 | `make catalog-sql` |
| 실행 이력 (DAG 단위 / 소스 단위 분리) | 완료 | `make demo-fail-source` |
| 품질 결과 (통과·실패 모두 적재) | 완료 | `make catalog-verify` |
| 소유자·분류를 별도 테이블로 분리 | 계획 | 자산 6종·팀 하나 규모에서는 조인 비용이 이득을 넘습니다 |
| 인덱스 설계 | 완료 | `make catalog-bench` |

테이블 13개입니다. 설계 근거는 [카탈로그 문서](../docs/metadata-catalog.md)에 있습니다.

## 5. 외부 시스템 연동

JD 의 SAP·Salesforce·사내 DB 같은 업무 시스템 연동은 **하지 않았습니다.**

대상이 이 프로젝트가 만드는 운영 데이터 6종이라 커넥터가 필요 없었습니다. 다만 설계상 바뀌는 지점은 정리해 뒀습니다.

| 바뀌는 것 | 지금 | 업무 시스템이 붙으면 |
|---|---|---|
| 수집 방식 | HTTP 폴링 | CDC·증분 추출·전체 적재 혼합 |
| 스키마 출처 | 관측한 payload | 원천 DDL 또는 API 스키마 |
| 개인정보 | 없음 | 분류와 마스킹이 필수 |
| 소유자 | 한 팀 | 시스템별로 다름 → 테이블 분리 필요 |

위 표의 **소유자·분류 테이블 분리**가 계획으로 남은 이유가 여기 있습니다. 지금 나누면 조인 비용만 늘고, 업무 시스템이 붙는 순간 반드시 필요해집니다. 그 시점을 염두에 두고 `qualified_name` 을 유일 키로 잡아 뒀습니다.

## 6. 남은 것을 우선순위로

1. **질의 정확도 평가셋** — MCP 가 틀린 답을 해도 알아차릴 방법이 없습니다. 가장 위험한 공백입니다
2. **알림 연동** — 검사가 잡아도 사람이 조회해야만 압니다
3. **검사 정의의 DB 이관** — 검사를 추가하려면 코드를 고쳐야 합니다
