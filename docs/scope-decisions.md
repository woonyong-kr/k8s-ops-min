# 범위 판단

이 저장소에 **없는 것**을 적은 기록입니다. 지운 이유를 남기지 않으면 다음 사람이 같은 판단을 다시 해야 합니다.

## AI 조회 도구 계층 — 만들었지만 최종 경로에서 빠졌습니다

### 무엇을 만들었나

AI가 운영 데이터를 조회하도록 내부 도구 계층을 만들었습니다. 클러스터 현황, 로그 근거, 배포 상태, 원인 판정 결과를 도구로 노출했습니다. 도구 75개, 약 6,300줄입니다.

→ [`src/services/mcp/internal_control/`](../src/services/mcp/internal_control/)

만들면서 두 가지를 지켰습니다.

**기존 API를 거치게 했습니다.** 도구가 DB나 클러스터에 직접 붙으면 기존 인증과 인가를 우회합니다.

**변경 도구는 기본으로 껐습니다.** 조회와 변경을 나누고, 변경 도구는 `OPSIA_MCP_ENABLE_WRITES` 를 명시적으로 켜야만 노출되게 했습니다. AI 실행 경로에서는 변경 *제안*까지만 허용하고 최종 제출은 사람 승인 단계로 분리했습니다.

### 왜 최종 경로에서 빠졌나

프로젝트 후반에 제품 범위를 좁혔습니다. 여러 장애 유형을 얕게 다루는 대신 **한 장애 경로를 증거 수집부터 복구 검증까지 끝까지 완성**하기로 했습니다.

이 계층은 gateway와 AI runtime에 연결됐지만, 최종 시연의 Golden Path와 수용 조건에는 포함되지 않았습니다. 연결 코드가 있는 것과 실제 사용자 흐름에서 검증된 것은 다릅니다.

### 왜 지우지 않았나

지우는 편이 저장소는 깔끔해집니다. 실제로 정리본에서는 지웠습니다.

여기서는 남겼습니다. 코드가 없으면 "만들었는데 안 썼다"는 말을 검증할 방법이 없기 때문입니다. 판단의 근거가 사라지면 판단만 남고, 판단만 남은 문장은 확인할 수 없습니다.

**대신 완성된 사용자 성과로 세지 않습니다.** 단위·경계 테스트와 연결 코드는 있지만 최종 시연 경로와 사용성 검증이 없습니다. 도구 개수와 줄 수는 규모지 완성도가 아닙니다.

### 카탈로그에서는 다시 붙였습니다

후속 카탈로그 확장에 같은 성격의 읽기 도구가 추가됐습니다. 아직 실제 사용자는 없고, 예상 소비자와 질문만 정의한 상태입니다.

| | 팀 프로젝트 도구 계층 | 카탈로그 MCP |
|---|---|---|
| 조회 대상 | 운영 데이터 | 자산·스키마·리니지·품질 |
| 질문의 성격 | 원인 판정 규칙이 이미 처리 | 자연어로 던지는 탐색적 질문 |
| 실사용자 | 없음 | **아직 없음.** 상정한 것이지 관측한 것이 아닙니다 |
| 잘못됐을 때 알아차릴 방법 | 없음 | **부분적.** 감사 로그는 남지만 질의 정확도 평가셋이 없습니다 |
| 도구의 역할 | 기존 운영 API를 AI 도구로 노출 | 구현된 카탈로그 API 계약을 노출하도록 설계 |
| 잘못됐을 때 결과 | 없던 경로가 생김 | 잘못된 답이 나올 뿐 |

두 번째도 제 기준을 완전히 만족하지는 못했습니다. 만든 이유는 **잘못됐을 때의 결과가 다르다**고 봤기 때문입니다.

그래서 규칙에 조건을 하나 더했습니다.

> 소비자가 없으면 만들지 않는다. 단 **되돌릴 수 있고 부작용이 없다면** 만들되 그 사실을 문서에 남긴다.

이건 규칙을 지킨 게 아니라 **예외를 만들고 근거를 적은 것**입니다. 그렇게 적는 편이 정확합니다.

솔직히 말하면 순서도 반대였습니다. MCP를 만들 자리를 찾다가 카탈로그가 가장 덜 억지스러운 곳이라 거기 붙였고, 붙이고 나서 근거를 정리했습니다. 결과적으로 근거가 성립한다고 보지만, **결론이 먼저였다는 사실 자체는 남겨 둡니다.**

평가셋을 만들어 두 번째 기준을 채우는 것이 다음 과제입니다. 구현은 [관련 문서](catalog-api-mcp.md)에 있습니다.

## 그 외 제외한 범위

| 제외한 것 | 이유 |
|---|---|
| 모든 Kubernetes 장애의 자동 복구 | 규칙으로 판정 가능한 한 경로만 완성하는 편이 검증 가능하다 |
| AI의 자유로운 manifest 수정 | 변경 가능한 필드를 허용 목록으로 고정하는 쪽이 안전하다 |
| 클러스터 직접 변경과 자동 병합 | 변경 제안까지만 하고 확정은 사람이 한다 |
| 자연어 → SQL 생성 | 생성된 질의의 정확성을 검증할 방법이 없습니다. [리서치](tech-research.md#4-llm-연동-범위) |
| 외부 카탈로그 도구 도입 | 자산 6종 규모에서 운영 비용이 이득을 넘습니다. 자체 카탈로그를 만든 것과 모순이 아닙니다 — 아래 구분 참조. [리서치](tech-research.md#2-데이터-카탈로그) |
| 범용 채팅, 웹 터미널 | 장애 분석과 직접 이어지지 않는다 |
| 비용·트래픽 대시보드 | 이 제품이 답해야 할 질문이 아니다 |

## 여기서 배운 것

기능 수는 완성도가 아니었다. 오히려 기능이 늘수록 **각 기능이 어떤 조건에서 신뢰할 수 있는지 설명하기 어려워졌다.**

규칙을 만들고 나서 배운 게 하나 더 있습니다. **규칙을 어겼다는 사실을 숨기는 것이 규칙을 어기는 것보다 나쁩니다.**

위 표에서 카탈로그 MCP 행을 비워 두거나 "실사용자: 카탈로그를 뒤지는 사람"이라고 적었다면 문서는 더 깔끔했을 겁니다. 그건 이 저장소가 [데이터에 대해 주장하는 것](collection-contract.md)과 정반대입니다.

## 외부 카탈로그 도구를 안 쓴 것과 카탈로그를 만든 것

이 둘이 충돌해 보일 수 있어 구분해 적습니다.

| | 외부 카탈로그 도구 | 이 저장소의 카탈로그 |
|---|---|---|
| 무엇 | OpenMetadata · DataHub 같은 제품 | 테이블 13종 + 검사 8종 + 조회 API |
| 비용 | 별도 배포 · 운영 · 학습 | 스키마 몇 개 |
| 주는 것 | 검색 UI, 조직 전체 통합, 플러그인 생태계 | 대조 기준, 상태 요약 |
| 자산 6종 규모에서 | **비용이 이득을 넘습니다** | **이득이 큽니다** |

"카탈로그가 필요 없다"가 아니라 **"제품을 들일 만큼은 아니다"** 입니다.

자체 카탈로그가 이득인 근거는 측정으로 남아 있습니다. 같은 질문("이 자산 마지막 관측이 언제인가")에 답할 때 관측 이력에서 매번 계산하면 223.9ms, 카탈로그에서 조회하면 0.106ms 입니다. 소비자가 늘수록 그 차이가 곱해집니다.
