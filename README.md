# Kyro

Kubernetes 장애가 발생했을 때 관련 증거를 수집하고, 규칙으로 원인을 판정하고, 허용된 범위의 수정안을 GitHub Draft PR로 제안한 뒤 배포 결과를 다시 확인하는 도구입니다.

크래프톤 정글 12기 SW-AI Lab 최종 프로젝트입니다. 5인 팀, 2026년 6~7월. 이 문서는 그중 이민정이 맡은 범위와 그 과정에서 내린 판단을 정리한 것입니다.

```
증거 수집 ──▶ 원인 판정 ──▶ 수정안 Draft PR ──▶ 배포 후 재확인
   │                                                    │
   └────────────────── 문제가 남아 있으면 ◀──────────────┘
```

완결한 흐름은 하나입니다. `ImagePullBackOff → 잘못된 이미지 태그로 판정 → 태그 수정 Draft PR → 재수집으로 확인`.

## 맡은 범위

네 단계 중 **증거 수집**을 담당했습니다. 원인 판정, 수정안 제안, 배포 후 재확인은 팀원이 맡았습니다.

증거는 Kubernetes API, Prometheus, Loki, Tempo 네 곳에서 옵니다. 네 시스템은 응답 형식도, 시간 기준도, 실패하는 방식도 다릅니다. 이걸 하나의 형식으로 모으고, 각 증거를 어디까지 믿어도 되는지 함께 전달하는 것이 제 일이었습니다.

원인 판정은 제가 준 증거를 근거로 돌아갑니다. 증거가 절반만 수집됐다는 사실을 알리지 않으면 판정도 절반짜리 근거로 결론을 냅니다. 아래 문제들은 대부분 이 지점에서 나왔습니다.

프로젝트가 끝난 뒤에는 수집된 데이터를 매일 다시 검사하는 배치와 메타데이터 카탈로그를 개인 작업으로 추가했습니다.

## 다룬 문제

각 항목은 무슨 일이 있었는지까지만 적었습니다. 어떻게 풀었는지는 링크에 있습니다.

### 잘린 목록 하나가 멀쩡한 리소스를 삭제했습니다

자료가 없는 경우, 볼 권한이 없는 경우, 시간 초과로 못 가져온 경우가 전부 빈 목록으로 돌아왔습니다. 받는 쪽이 해야 할 일은 다섯 가지였는데 구분할 방법이 없었습니다.

저장소가 잘린 목록을 받고 "여기 없으니 삭제된 것"으로 판단했습니다.

지금은 그 판단이 코드에서 막힙니다. → [무엇을 어떻게 막았는지](docs/portfolio/01-collection-contract.md)

### 앞에서부터 100개를 자르면 뒤쪽 namespace가 전멸합니다

클러스터가 커지자 한 번 조회에 수천 건이 돌아왔습니다. 자르지 않으면 전송이 실패합니다.

그런데 순서대로 자르면 특정 그룹만 통째로 빠지고, 받는 쪽은 그게 전부라고 생각합니다. 위의 삭제 사고가 여기서 시작됐습니다.

자르되 편향과 은폐를 동시에 없애야 했습니다. → [어떤 순서로 잘랐는지](docs/portfolio/02-collection-limits.md)

### 지울 필드를 열거하는 방식은 제가 아는 만큼만 안전했습니다

설정 장애를 조사하려면 어느 워크로드가 어떤 Secret을 쓰는지 알아야 합니다. 저장된 배포 정보를 그대로 반환하면 Secret 값도 함께 나갑니다.

그래서 지울 필드를 하나씩 적었습니다. 나중에 `metadata.annotations` 안에서 이전 manifest 전체가 평문 환경변수를 포함한 채 발견됐습니다. 제가 열거하지 못한 경로였습니다.

방식을 뒤집었습니다. → [무엇을 어떻게 뒤집었는지](docs/portfolio/03-config-reference-api.md)

### 수집은 계속 성공하는데 데이터는 어긋나고 있었습니다

원천의 필드 타입이 바뀌어도 수집은 성공합니다. 새 데이터가 하나도 없어도 실행 이력은 정상입니다. 더 이상 쓰지 않는 자산이 목록에만 남아 있어도 아무도 모릅니다.

실행이 실패하지 않으니 알림도 울리지 않습니다. 사람이 알아차릴 때는 이미 그 데이터로 만든 결과가 나간 뒤입니다.

프로젝트가 끝난 뒤 개인 작업으로 매일 재검사하는 배치를 붙였습니다.
→ [매일 무엇을 대조하는지](docs/portfolio/04-metadata-catalog.md) · [배치를 어떻게 돌렸는지](docs/portfolio/05-airflow-pipeline.md) · [검사 SQL](docs/portfolio/06-sql-quality-checks.md) · [조회 API와 MCP](docs/portfolio/07-catalog-api-mcp.md)

### 만든 기능이 최종 경로에서 빠졌습니다

AI가 운영 데이터를 조회하는 도구 계층을 만들었습니다. 도구 75개, 약 6,300줄입니다. 그런데 프로젝트 후반에 제품 범위를 한 장애 경로로 좁히면서 이 계층은 어느 흐름에도 들어가지 않게 됐습니다.

코드는 `src/services/mcp/internal_control/` 에 남아 있습니다. 지우지 않은 이유와, 그럼에도 "완성한 기능"으로 세지 않는 이유를 적었습니다.

카탈로그에는 같은 성격의 도구를 다시 붙였습니다. 이번엔 조회할 사람이 있었습니다.

→ [기준과 예외](docs/portfolio/09-scope-decisions.md)

## 실행

Python 3.13, [uv](https://docs.astral.sh/uv/), Docker가 필요합니다.

```bash
uv sync --all-groups
```

배치와 카탈로그는 AWS 계정이나 실제 클러스터 없이 로컬에서 동작합니다.

```bash
make catalog-up        # Airflow, PostgreSQL, MinIO 기동
make catalog-seed      # 검증용 fixture 적재
make catalog-run       # DAG 1회 실행
make catalog-verify    # 아래 항목 검증
make catalog-sql       # 정합성 검사 SQL 실행
```

`make catalog-verify`는 다음을 확인합니다.

- 같은 논리 날짜를 3회 재실행해도 상태 테이블 행 수가 변하지 않는지
- Loki 수집을 강제로 실패시켰을 때 `PARTIAL`이 기록되고 나머지 세 소스는 적재되는지
- 실패한 task만 다시 실행했을 때 성공한 소스가 중복되지 않는지
- 검증 단계를 강제로 실패시켰을 때 적재 0건인 실행이 성공으로 남지 않는지
- fixture의 필드 타입을 바꿨을 때 스키마 드리프트가 검출되는지
- 정규화 행에서 S3 원본 객체까지 역추적되는지
- 정상 fixture에서 모든 검사가 0행을 반환하는지

마지막 항목이 필요한 이유는, 문제 있는 데이터로만 시험하면 항상 문제라고 답하는 검사도 통과하기 때문입니다.

전체 프로젝트는 다음으로 확인합니다.

```bash
make demo              # Golden Path 계약 테스트
make test              # Ruff, compileall, pytest
make gate              # 저장소 전체 검사
make manifest-check    # Helm lint, RBAC 검증
```

## 판단이 바뀐 지점

5주 동안 작업 순서가 네 번 바뀌었습니다.

수집기를 붙이기 전 화면 개발용으로 넣어 둔 가짜 데이터를, Prometheus 연동이 동작하기 시작한 날 먼저 지웠습니다. 가짜 데이터가 남아 있으면 수집이 실패해도 화면이 정상으로 보입니다. 그 뒤로는 기능을 확인하기 전에 실패가 실패로 보이는지부터 확인하게 됐습니다.

응답 한도를 provider마다 붙이다가 네 번째에서 같은 코드를 또 쓰고 있다는 걸 알아차리고 공통 모듈로 뽑았습니다. 그 뒤로는 같은 코드가 두 번째로 나오면 멈추고 공통화합니다.

설정 참조 API를 만들고 40분 뒤 코드 리뷰에서 경계 조건 지적을 받았습니다. 기능은 전부 검증했는데 비정상적으로 큰 입력을 확인하지 않았습니다. 그 뒤로는 기능 테스트를 쓰고 나서 경계 입력을 먼저 묻습니다.

프로젝트가 끝난 뒤 설정 참조 API를 다시 보면서, 검증이 "제가 생각한 경로에서 새지 않는다"까지만 증명하고 있다는 걸 알았습니다. 방식을 바꿔 카나리 토큰을 심자 열거로는 찾지 못했을 경로가 바로 걸렸습니다.

카탈로그 작업에서는 `trigger_rule`을 이름만 보고 잘못 이해했습니다. `none_failed_min_one_success`를 "하나라도 성공하면 진행"으로 읽었는데, Airflow 소스를 열어 보니 실패가 하나라도 있으면 건너뛰는 규칙이었습니다. 부분 실패를 보존한다는 설계가 그 상태로는 동작할 수 없었습니다. 지금은 규칙 이름에 조건을 맡기지 않고 task 본문에 조건을 적습니다.

커밋 단위 기록은 [엔지니어링 로그](docs/portfolio/10-engineering-log.md)에 있습니다. 도구 선택 근거는 [기술 리서치](docs/portfolio/08-tech-research.md)에 있습니다.

## 한계

조회 API가 Secret 값을 반환하지 않을 뿐, 스냅샷 저장소와 S3 원본에는 값이 남아 있습니다. 수집 단계에서 저장하지 않도록 바꾸지 못했습니다.

알림 연동이 없습니다. 지표는 조회만 가능하므로 모니터링을 구현했다고 쓰지 않았습니다.

데이터베이스 인덱스를 설계하지 않았습니다. 데이터가 누적되면 검사 질의가 전체 스캔합니다.

부하 한계를 측정하지 않았습니다. 응답 한도는 상한 계약이지 처리량 근거가 아닙니다.

실제로 반복 사용한 사용자가 없습니다. 시연에 성공한 것과 실제로 쓰인 것은 다릅니다.

카탈로그가 다루는 것은 이 프로젝트가 만드는 운영 데이터 6종입니다. 외부 업무 시스템 연동은 조사까지만 했습니다.

배치와 카탈로그는 프로젝트 종료 후 개인 작업이며 AI 코딩 도구를 함께 사용했습니다. 설계 판단과 검증은 직접 했습니다.

팀 저장소는 작업 중 이력 정리를 여러 차례 거쳤습니다. 커밋 수는 기여의 근거가 아닙니다. 기여 범위는 파일 단위 blame과 코드로 확인하는 편이 정확합니다.

## 배경

크래프톤 정글 SW-AI Lab 22주 과정을 수료했습니다. 자료구조와 알고리즘, Redis 구현, SQL, 메모리 할당기, 웹 프록시, PintOS, GPT 구현을 거쳐 팀 협업 서비스와 최종 프로젝트를 진행했습니다.

PintOS에서 page fault를 다루며 관측된 상태가 실제 상태와 다를 수 있다는 것을 처음 의식했습니다. 이 프로젝트에서 수집 결과에 신뢰 범위를 함께 담기로 한 것은 그 질문의 연장선입니다.
