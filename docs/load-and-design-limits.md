# 어디까지 재봤고 어디서 무너지는가

여러 문서의 「남은 것」 절에 `부하 한계를 재지 않았습니다`라고 적어 두고 있었습니다. 그 상태로는 만든 것이 어느 규모까지 쓸 수 있는지 저도 모릅니다.

행 수를 늘려가며 다시 쟀습니다. 결론부터 적으면 **관측 470만 행 / 3.4GB 까지 확인했고, 그 지점에서 검사 하나가 전체 시간의 80%를 씁니다.**

---

## 무엇으로 쟀나 — 합성 데이터입니다

먼저 밝혀 둘 것이 있습니다. **아래 수치는 합성 데이터로 잰 값입니다.**

`scripts/catalog_bench.py` 가 `generate_series` 로 행을 만듭니다. `cluster_id` 는 3종, `collection_status` 는 전부 `completed` 로 고정돼 있습니다. **균일 분포이고 skew 가 없습니다.**

실제 클러스터에서는 `resource_uid` 카디널리티와 상태 분포가 이와 다릅니다. 특히 08(3컬럼 GROUP BY)과 03(드리프트)은 카디널리티 분포에 직결되므로 **실측값은 여기서 나온 값과 다를 수 있습니다.** 아래 표는 "이 구조가 데이터 양에 따라 어떻게 자라는가"를 보는 용도이지 운영 성능 예측치가 아닙니다.

한 가지 더. 벤치마크는 `run_id` 하나로 02·03 을 재지만 실제 실행기(`checks.py`)는 dag_run 에 속한 **모든 run_id 를 루프**로 돕니다. 원천이 4개면 실제 배치의 02·03 비용은 측정값의 약 4배입니다. **합계 2,590ms 는 배치 전체 시간이 아닙니다.**

## 어디까지 쟀나

| | 1차 | 2차 | 배 |
|---|---:|---:|---:|
| `observed_fields` | 603,618 | 4,667,754 | 7.7x |
| `observed_rows` | 120,762 | 939,213 | 7.8x |
| `normalized_evidence` | 60,762 | 470,421 | 7.7x |
| 테이블 총 크기 | 313 MB | **3,463 MB** | 11x |
| 검사 8종 + 조회 2종 합계 | 150.0 ms | **2,590.3 ms** | **17.3x** |

**데이터가 7.7배 늘 때 검사 시간은 17.3배 늘었습니다. 선형이 아닙니다.**

## 어느 질의가 자라나

| 질의 | 60만 행 | 470만 행 | 배 |
|---|---:|---:|---:|
| 08 중복 적재 후보 | 95.7 | **2,068.3** | 21.6x |
| 05 최신성 위반 | 29.7 | 239.6 | 8.1x |
| 90 리소스별 최신 상태 | 14.2 | 157.4 | 11.1x |
| 91 리니지 역추적 | 0.8 | 78.4 | **98x** |
| 03 스키마 드리프트 | 2.5 | 23.1 | 9.2x |
| 02 필수 필드 누락 | 4.0 | 18.9 | 4.7x |
| 01 원천 커버리지 | 0.9 | 1.3 | 1.4x |
| 04 버전 미갱신 변경 | 0.6 | 0.6 | 1.0x |
| 06 리니지 단절 | 0.6 | 1.1 | 1.8x |
| 07 실행 정합성 | 1.0 | 1.6 | 1.6x |

**넷은 데이터가 늘어도 안 자랍니다.** 01·04·06·07은 470만 행에서도 1ms 대입니다. 등록 정보와 실행 이력만 보는 질의라 관측 데이터가 늘어도 영향이 없습니다.

**08이 전체의 80%를 씁니다.** 2,590ms 중 2,068ms입니다.

**91 재귀 CTE 는 기울기가 가장 급합니다.** 절대값은 78ms 로 작지만 98배로 늘었습니다. 간선이 313개인 지금이 그렇습니다. 간선이 늘면 여기가 먼저 문제가 됩니다.

## 갈린 지점은 SQL 이 아니라 데이터 모델이었습니다

측정값을 보고 처음에는 "느린 질의를 튜닝하면 되겠다"고 생각했습니다. 그런데 검사별로 **어느 테이블을 읽는지** 세어 보니 답이 달랐습니다.

| 검사 | 읽는 테이블 | 470만 행에서 | 배 |
|---|---|---:|---:|
| 01 원천 커버리지 | 메타데이터만 | 1.3 ms | 1.4x |
| 04 버전 미갱신 변경 | 메타데이터만 | 0.6 ms | 1.0x |
| 06 리니지 단절 | 메타데이터만 | 1.1 ms | 1.8x |
| 07 실행 정합성 | 메타데이터만 | 1.6 ms | 1.6x |
| 02 필수 필드 누락 | `observed_rows` · `observed_fields` | 18.9 ms | 4.7x |
| 03 스키마 드리프트 | `observed_fields` | 23.1 ms | 9.2x |
| 90 리소스별 최신 상태 | `normalized_evidence` | 157.4 ms | 11.1x |
| 05 최신성 위반 | `normalized_evidence` · `observed_rows` | 239.6 ms | 8.1x |
| 08 중복 적재 후보 | `normalized_evidence` | 2,068.3 ms | 21.6x |

**예외가 하나도 없습니다.** 관측 데이터를 안 읽는 넷은 안 자라고, 읽는 다섯은 자랍니다.

### 왜 이렇게 나뉘었나

카탈로그 테이블을 설계할 때 두 부류로 나눴습니다.

| 부류 | 무엇 | 무엇에 비례해 자라나 |
|---|---|---|
| 등록 정보 · 실행 이력 | 자산 / 필드 계약 / 원천 / 실행 | **자산 수 × 계약 변경 횟수** — 느림 |
| 관측 데이터 | `observed_rows` · `observed_fields` · `normalized_evidence` | **리소스 수 × 실행 횟수** — 빠름 |

나눈 이유는 성능이 아니었습니다. **"등록한 것"과 "관측한 것"을 대조하려면 둘이 다른 테이블에 있어야 하기 때문**입니다. 같은 테이블에 두면 대조할 기준이 사라집니다.

그런데 결과적으로 **자라는 속도가 다른 두 축을 갈라 놓은 셈**이 됐습니다. 그리고 검사가 어느 쪽을 읽느냐가 그 검사의 확장성을 결정했습니다.

**이건 SQL 을 짜기 전에 이미 정해진 것입니다.** 튜닝으로 바꿀 수 있는 게 아닙니다. 01·04·06·07 이 빠른 건 질의를 잘 써서가 아니라 **읽는 대상이 작기 때문**입니다.

여기서 얻은 기준은 이겁니다.

> 검사를 새로 만들 때 먼저 물어야 할 것은 "이 질의가 빠른가"가 아니라 **"이 검사가 관측 데이터를 읽어야만 하는가"** 입니다. 안 읽어도 되면 그 검사는 규모와 무관해집니다.

## 08 — 중복 판정을 언제 할 것인가

### 처음에 왜 이렇게 만들었나

중복 적재를 막는 방법은 둘입니다.

**적재하는 순간 막기** — 유일 제약을 걸면 두 번째 행이 안 들어옵니다.
**적재한 뒤 찾기** — 들어온 것을 나중에 조회해서 판정합니다.

`(cluster_id, source_id, resource_uid, observed_at)` 에 유일 제약을 걸어 놨습니다. **정확히 같은 관측은 이미 막힙니다.**

그런데 재시도나 backfill 이 만드는 중복은 이 제약을 통과합니다.

```
원본     06-01 03:00:00   uid-7
재시도   06-01 03:00:03   uid-7     ← 3초 차이. 유일 제약 통과
```

원천이 타임스탬프를 다시 계산하면 관측 시각이 미세하게 달라집니다. **논리적으로는 같은 관측인데 제약은 다르다고 봅니다.**

### 여기서 갈렸습니다

| 안 | 어떻게 | 대가 |
|---|---|---|
| 저장 시점에 막기 | `observed_at` 을 초·분 단위로 버려서 유일 키에 넣는다 | **원본 시각이 사라집니다.** 그리고 뭉갤 단위를 미리 정해야 합니다 |
| 조회 시점에 찾기 | 원본 그대로 저장하고 검사로 판정한다 | **전체를 읽어야 합니다** |

**조회 시점을 골랐습니다.** 기준은 하나였습니다.

> 되돌릴 수 있는 쪽을 고른다.

뭉개는 단위를 잘못 정하면 **되돌릴 수 없습니다.** 이미 버린 시각은 복구가 안 됩니다. 그리고 원천이 넷인데 각각 타임스탬프 정밀도가 다릅니다. Prometheus 는 초 단위, Kubernetes API 는 `resourceVersion` 기준이라 시각이 아예 다른 축입니다. **하나의 단위로 뭉갤 수가 없습니다.**

원본을 그대로 두면 나중에 판정 기준을 바꿀 수 있습니다. 실제로 한 번 바꿨습니다 — 처음에는 시각까지 포함해 묶었다가 아무것도 못 잡는다는 걸 알고 날짜 단위로 바꿨습니다.

### 어떻게 알게 됐나

행 수를 늘려 재기 전까지는 몰랐습니다. 60만 행에서 95.7ms 였고 그건 문제로 보이지 않았습니다.

470만 행에서 2,068ms 가 나온 뒤 실행 계획을 봤습니다.

```
Rows Removed by Filter: 470421
->  Index Only Scan  (actual rows=470421)
```

**결과가 0행인데 47만 행을 전부 읽고 전부 버립니다.** 기간 조건이 `HAVING` 에 있어서 읽기 전에 못 거릅니다.

기간 조건을 `WHERE` 로 내리면 되지 않느냐고 물으면, 그러면 이 검사가 잡아야 할 사례를 놓칩니다.

```
원본     06-01 관측, 06-01 적재
복제본   06-01 관측, 07-30 적재     ← backfill 이 만든 중복

WHERE ingested_at >= 최근 2일  →  원본이 걸러져 복제본만 남는다
                                  → "1건짜리 그룹" 이라 중복으로 안 잡힌다
```

**정확성과 스캔량이 정면으로 부딪힙니다.**

### 무엇을 선택했나

둘 다 포기하지 않는 방법을 찾았습니다. **두 단계로 나눕니다.**

1. 최근 적재분에서 **후보 키만** 뽑습니다 (`cluster_id`, `source_id`, `resource_uid`, 날짜)
2. 그 키만 놓고 **전체 기간**을 조회합니다

원본이 5일 전이어도 복제본이 어제 들어왔다면 2단계에서 같은 그룹으로 묶입니다.

**공짜는 아닙니다.** 1단계가 "최근 2일 안에 적재된 것"으로 후보를 좁히므로, 원본과 복제본이 **둘 다** 그보다 오래전에 적재된 중복은 후보에 들어오지 않습니다. 전량 GROUP BY 는 잡던 경우입니다. 검사를 매일 돌리는 한 중복이 생긴 날 안에 창 안으로 들어오므로 실제로 새는 것은 배치가 이틀 넘게 멈춘 뒤 재개될 때입니다. 그때는 창을 넓혀 한 번 돌려야 합니다. 이 사각지대는 테스트로 고정해 뒀습니다(`test_두_단계_질의는_적재_창_밖의_중복을_놓친다`) — 창이 바뀌면 그 테스트가 먼저 깨집니다.

아래는 `ARRAY_AGG` 없이 판정 조건만 남기고 `EXPLAIN ANALYZE` 로 잰 값입니다. 위 표의 2,068ms 는 실제 검사가 반환하는 컬럼을 전부 포함한 값이라 더 큽니다. 두 방식을 같은 조건에서 비교한 것이 이 표입니다.

| | 실행 시간 |
|---|---:|
| 현재 (전체 GROUP BY) | 810 ms |
| 2단계 질의 | 673 ms |
| 2단계 + `ingested_at` 인덱스 | **460 ms** |

470만 행 중 최근 2일 적재분이 41,221행(8.8%)일 때 1.76배입니다. 운영에서는 하루 적재분 비율이 이보다 낮으므로 효과가 커집니다.

**적용했습니다.** 바꾸기 전에 결과가 같은지부터 확인했습니다 — 원본이 5일 전이고 복제본만 최근인 쌍까지 두 질의가 똑같이 잡는 것을 실제 데이터로 대조하고 테스트로 고정했습니다(`test_중복_검사가_두_단계여도_같은_것을_잡는다`). 완전히 같지는 않다는 것도 위에 적은 대로 테스트에 남겼습니다. 빠른 것보다 **무엇을 내주는지 아는 것이 먼저**입니다.

아래 표의 2,590ms 는 적용 전 측정값입니다. 적용 후 수치는 다시 재지 않았습니다.

## 91 — 순환을 정확히 막으려다 비싸진 경우

리니지 역추적은 재귀 CTE 입니다. 470만 행 측정에서 78.4ms 로 절대값은 작지만 **기울기가 가장 급했습니다.**

간선은 313개뿐입니다. 데이터가 커서 느린 게 아닙니다.

### 왜 비싼가

순환 참조를 막으려고 **지나온 경로를 배열로 들고 다닙니다.**

```sql
ARRAY[l.downstream_asset_id, l.upstream_asset_id] AS path
...
WHERE NOT l.upstream_asset_id = ANY(u.path)
  AND u.depth < 10
```

`= ANY(배열)` 은 배열을 훑습니다. 경로가 깊어질수록 배열이 길어지고, **경로 수만큼 이 비교가 일어납니다.** 다이아몬드 구조에서는 경로가 지수적으로 늘 수 있습니다.

### 대안은 있었나

| 안 | 어떻게 | 대가 |
|---|---|---|
| depth 제한만 | 경로 배열 없이 깊이만 자른다 | 순환이 있으면 **같은 조상을 반복 반환**합니다 |
| 경로 배열 | 지나온 노드를 기억한다 | **경로 수에 비례해 비쌉니다** |
| closure table | 조상 관계를 미리 계산해 저장한다 | 간선이 바뀔 때마다 **재계산**해야 합니다 |

경로 배열을 골랐습니다. 기준은 이거였습니다.

> 자산이 6종이고 리니지 깊이가 3단계입니다. 미리 계산해 저장할 만큼 조회가 잦지 않고, 대신 간선은 매 실행마다 갱신됩니다.

**조회가 드물고 갱신이 잦으면 조회 때 계산하는 쪽이 맞습니다.** closure table 은 반대 상황을 위한 것입니다.

### 그런데 조건이 바뀌면

이 판단은 **자산 6종 · 깊이 3단계**에 묶여 있습니다. 자산이 수백 개가 되거나 리니지가 깊어지면 뒤집힙니다.

지금 안전장치는 `depth < 10` 하나뿐입니다. 그마저도 **깊이만 자르고 폭은 안 자릅니다.** 한 자산이 upstream 을 수십 개 갖는 구조가 되면 경로 수가 폭발합니다.

측정에서 기울기가 가장 급하게 나온 이유가 이것입니다. **여기가 이 시스템에서 가장 먼저 무너질 지점입니다.** 절대값이 작아서 지금은 안 보일 뿐입니다.

## 수억 행에서는 어떻게 되나

**모릅니다. 이 수치를 외삽하면 안 됩니다.**

근거를 적습니다.

**08 은 전체 스캔이라 데이터에 거의 비례합니다.** 470만 행 2.0초를 그대로 늘리면 1억 행에서 40초가 넘습니다. 그런데 그 구간에서는 `work_mem` 을 넘겨 디스크 정렬로 떨어지므로 실제로는 더 나빠집니다. 지금 측정은 메모리 안에서 끝난 값이라 **그 변곡점 이후를 예측할 수 없습니다.**

**91 재귀 CTE 는 간선 수에 따라 급격히 자랍니다.** 313개에서 78ms 이고 기울기가 98배였습니다. 깊이 제한이 없어서 간선이 순환하거나 깊어지면 어디까지 갈지 알 수 없습니다.

**측정 환경이 단일 인스턴스입니다.** 동시 실행, 다른 워크로드와의 경합, 커넥션 풀 포화는 재보지 않았습니다.

## 카탈로그를 정리하면 — 없는 계층이 하나 있습니다

측정 결과를 들고 카탈로그 테이블 13종을 성격별로 다시 나눠 봤습니다.

| 계층 | 테이블 | 무엇에 비례해 자라나 |
|---|---|---|
| **등록** | `data_sources` · `data_assets` · `asset_fields` | 자산 수 — 거의 안 자람 |
| **실행 이력** | `dag_runs` · `collection_runs` · `loads` · `quality_results` | 실행 횟수 — 느리게 자람 |
| **관측 이력** | `observed_rows` · `observed_fields` · `normalized_evidence` · `raw_snapshots` · `schema_observations` · `lineage_edges` | **리소스 × 실행 — 빠르게 자람** |
| **상태** | — | **없습니다** |

**"지금 어떤 상태인가"를 담는 계층이 통째로 빠져 있습니다.** 그래서 그 질문이 올 때마다 관측 이력을 훑습니다.

필드 계약에는 이미 이 분리가 있습니다. `asset_fields`(지금 계약)와 `schema_observations`(언제 바뀌었나)로 나눠 놨습니다. **같은 원칙을 관측에는 적용하지 않았습니다.**

### 조회 계층은 이미 증명하고 있습니다

조회 API 와 MCP 가 읽는 테이블을 세어 봤습니다.

```
조회 API   data_assets · dag_runs · quality_results
           data_sources · collection_runs · schema_observations
MCP 도구   list_data_sources / search_assets / get_asset_schema
           get_asset_lineage / list_quality_issues / get_run_status
```

**관측 이력을 하나도 읽지 않습니다.** 그래서 빠릅니다. 느린 것은 검사뿐이고, 검사만 아직 원본을 직접 훑습니다.

```
[지금]
관측 이력 ─┬─▶ 검사               47만 행 직접 스캔
           └─▶ 등록·실행 이력 ─┬─▶ 조회 API
                                └─▶ MCP

[정리 후]
관측 이력 ──▶ 카탈로그(등록·상태·요약) ─┬─▶ 검사
                                         ├─▶ 조회 API
                                         └─▶ MCP
```

상태 계층을 추가하는 것은 새 최적화가 아니라 **카탈로그를 절반만 만든 것을 마저 만드는 일**입니다.

### 정리하면서 같이 처리할 것

**`latest_state` 는 조회 API 와 MCP 가 씁니다.** `GET /v1/catalog/resources/state` 와 MCP `get_resource_state` 가 이 질의를 실행합니다. 한때 이 문서에 "소비자가 없으니 빼라"고 적혀 있었는데, 라우트를 붙인 뒤 여기를 고치지 않은 것이었습니다. 벤치마크 합계 2,590ms 중 157ms 는 실제로 응답에 쓰이는 시간입니다.

→ 상태 테이블이 생기면 이 질의는 그 테이블 조회로 바뀝니다. 라우트와 도구는 그대로 두고 안쪽만 갈아 끼웁니다.

## 상한을 만드는 법 — 계층형 보존

상태 테이블은 "훑지 않게" 하지만 **"쌓이지 않게" 하지는 못합니다.** 관측 이력에 삭제 정책이 없어서 지금도 무한히 자랍니다. 상한이 없으면 어떤 최적화도 시간을 벌 뿐입니다.

시계열 시스템이 쓰는 방식이 있습니다. **계층형 보존과 롤업**입니다.

| 계층 | 보관 | 무엇 | 용도 |
|---|---|---|---|
| Hot | 24시간 | 원본 행 | 당일 검사 |
| Warm | 90일 | **1시간 단위 요약** | 최신성·중복·드리프트 판정 |
| Cold | 무기한 | 일·월 단위 요약 | 추세, 감사 |
| Archive | 무기한 | S3 원본 (일자 파티션) | 재처리, 역추적 |

### 1시간 요약에 무엇을 담나

이 데이터는 수치 지표가 아니라 **관측 사실**입니다. 최저·평균·최대가 아니라 이런 것이 들어갑니다.

```
(cluster_id, source_id, resource_uid, hour)
  → 관측 건수
    고유 run_id 수            ← 08 중복 판정
    최초 · 최종 관측 시각      ← 05 최신성
    상태별 건수 (completed / partial / failed)
    관측된 스키마 해시 집합     ← 03 드리프트
```

수집 주기가 30초면 시간당 120관측입니다. **1시간 요약은 120:1 압축**입니다.

### 검사별로 어느 계층에서 답이 나오나

| 검사 | 필요한 것 | 어디서 |
|---|---|---|
| 05 최신성 | 마지막 관측 시각 | 상태 테이블 |
| 90 리소스 최신 상태 | 리소스별 최신 행 | 상태 테이블 |
| **08 중복 적재** | 같은 키를 몇 개 run 이 넣었나 | **1시간 요약** |
| 03 스키마 드리프트 | 관측된 필드·타입 집합 | 1시간 요약 |
| 01 · 04 · 06 · 07 | 등록 정보 · 실행 이력 | 이미 메타데이터 |
| **02 필수 필드 누락** | 개별 행에 그 필드가 있나 | **원본이 필요합니다** |

**08 이 요약으로 풀립니다.** 앞에서 "08 은 이력을 봐야 하므로 카탈로그로 못 푼다"고 적었는데, 시간 요약을 두면 풀립니다. `(키, 시간) → 고유 run 수` 를 유지하면 날짜 단위 합산으로 판정됩니다. 전체 스캔이 사라집니다.

`원본은 5일 전, 복제본은 어제` 케이스도 됩니다. 두 시간대 요약을 합치면 같은 키에 run 이 둘이니까요.

**02 만 원본이 필요합니다.** "이 행에 `name` 이 비어 있나"는 요약으로 답할 수 없습니다. Hot 24시간 안에서만 검사하고 그 이후는 못 한다고 정하면 됩니다. 지금도 실행 단위로만 봅니다.

### 압축 포맷을 정해야 합니다

"압축해 두면 검색도 편하다"는 포맷에 따라 갈립니다.

| 포맷 | 검색 |
|---|---|
| gzip · tar | **불편** — 전체 해제 후 스캔 |
| **Parquet + 일자 파티션** | **편함** — 필요한 컬럼·파티션만 읽음 |

`s3://.../date=2026-08-01/source=loki/*.parquet` 형태면 재처리할 때 그 날짜만 읽습니다. 지금 `.catalog-archive` 가 날짜별 JSON 이므로 Parquet 으로 바꾸면 됩니다.

### 이러면 상한이 생깁니다

| | 지금 | 계층형 적용 후 |
|---|---|---|
| Hot 원본 | 무한 누적 (470만 행 / 3.4GB) | **하루치로 고정** |
| Warm 요약 | 없음 | 90일 × 시간당 1행 (약 1/120) |
| 검사가 읽는 양 | 전체 | 상태 테이블 또는 요약 |
| 스토리지 | DB 에 계속 | S3 로 이동 |

**"데이터가 늘면 언젠가 무너진다"가 "하루치 크기만 관리하면 된다"로 바뀝니다.**

### 대가

**요약이 틀리면 되돌리기 어렵습니다.** 원본을 지운 뒤 요약 오류를 발견하면 S3 에서 재계산해야 합니다. **원본 삭제 전에 요약이 맞는지 확인하는 검사**가 필요합니다. 지금 검사들이 하는 일과 같은 성격입니다.

**요약 단위를 나중에 바꾸기 어렵습니다.** 1시간으로 정하고 원본을 지우면 5분 단위가 필요해도 못 만듭니다. S3 원본이 있어 재계산은 되지만 비용이 듭니다.

**backfill 이 요약을 갱신해야 합니다.** 과거 시간대에 데이터가 다시 들어오면 그 시간 요약을 다시 계산해야 합니다. 적재 시 upsert 로 처리합니다.

## 이 규모를 넘기려면

우선순위대로 적습니다.

1. **상태 계층 추가** — `asset_state` · `resource_state`. 효과가 가장 크고 다른 것과 독립적입니다. 위 표의 05(239.6ms) 와 90(157.4ms) 이 상태 테이블 조회로 바뀌므로 **397ms 가 빠집니다**. 상태 테이블 자체의 조회 시간은 아직 재지 않았습니다 — 테이블이 없으므로 잴 대상이 없습니다
2. **보존 정책** — 상한을 만드는 유일한 수단입니다. 이것 없이는 나머지가 시간을 벌 뿐입니다
3. **1시간 롤업** — 08 이 여기서 풀립니다. 2번과 함께 가야 의미가 있습니다
4. ~~**중복 적재 검사를 2단계 질의로**~~ — **적용했습니다**(1.76배). 다만 최근 2일 적재분에서 후보를 뽑으므로 원본과 복제본이 둘 다 그보다 오래전에 적재된 중복은 놓칩니다. 3번이 그 사각지대까지 없앱니다
5. **91 에 폭 제한** — 지금은 `depth < 10` 뿐이라 깊이만 자르고 폭은 안 자릅니다
6. **`latest_state` 를 상태 테이블 조회로 교체** — 1번을 하면 자연히 따라옵니다. 라우트와 도구는 그대로 둡니다

1번과 4번만으로 합계가 **2,590ms → 약 1,300ms** 가 됩니다. 계산은 이렇습니다 — 2,590.3 에서 05·90 의 397.0 을 빼면 2,193.3 이고, 여기서 08 의 2,068ms 를 1.76 로 나눈 1,175ms 로 바꾸면 1,300ms 입니다. 2·3번까지 가면 08 이 하루치 요약만 읽게 되므로 더 줄지만, **그 값은 재보지 않았습니다.** 롤업 테이블이 없어 잴 대상이 없습니다.

## 실제로 얼마나 돌았나

부하는 못 쟀지만 **가동 이력은 남아 있습니다.** 2026년 7월 AWS 청구서입니다.

| 항목 | 사용량 |
|---|---|
| CloudWatch 로그 수집 | 64.354 GB |
| Classic LoadBalancer | 2,150 시간 |
| NAT Gateway | 1,274 시간 |
| 사용 중 공인 IPv4 | 8,179 시간 |

7월은 744시간입니다. **공인 IPv4 8,179시간은 약 11개가 한 달 내내 붙어 있었다는 뜻**이고, 로그 64GB 는 시연 한 번으로 나오는 양이 아닙니다.

**반복 사용자를 확보했다는 뜻은 아닙니다.** 다만 "시연 한 번 하고 껐다"와는 다릅니다.

## 정리

| 질문 | 답 |
|---|---|
| 어디까지 재봤나 | 관측 470만 행 / 3.4GB |
| 그 지점에서 얼마나 걸리나 | 검사 8종 + 조회 2종 합계 2,590ms |
| 무엇이 확장성을 갈랐나 | 질의가 아니라 **읽는 테이블**. 관측 데이터를 읽는 5종만 자람 |
| 지금 가장 오래 걸리는 것 | 08 중복 적재 후보 (전체의 80%) |
| 왜 그런가 | 중복 판정을 저장 시점이 아니라 조회 시점에 두기로 했기 때문 |
| 왜 그렇게 골랐나 | 원천 4종의 타임스탬프 정밀도가 달라 뭉갤 단위를 고정할 수 없었음. 되돌릴 수 있는 쪽 선택 |
| 고쳤나 | 2단계 질의 적용 완료. 결과 동등성을 실제 중복 데이터로 확인하고 테스트로 고정 |
| 가장 먼저 무너질 곳 | 91 재귀 CTE. 절대값은 작지만 기울기가 가장 급하고 폭 제한이 없음 |
| 수억 행에서는 | 외삽 불가. 파티셔닝 없이는 안 됨 |

## 여기서 얻은 기준

- 검사를 만들 때 먼저 물을 것은 "이 질의가 빠른가"가 아니라 **"관측 데이터를 읽어야만 하는가"**
- 되돌릴 수 없는 최적화(원본을 뭉개서 저장)보다 되돌릴 수 있는 비용(조회 때 계산)을 먼저 고릅니다
- 조회가 드물고 갱신이 잦으면 조회 때 계산합니다. 반대면 미리 계산합니다
- 빠르게 만들기 전에 **잡던 것을 계속 잡는지**부터 확인합니다
