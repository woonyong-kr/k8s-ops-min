# 근거의 귀속 범위

> **① 자료 모으기 → ③ 자료 준비** · 5인 팀 프로젝트 · 담당 범위

원인 판정은 제가 준 증거로 돌아갑니다. 증거가 **잘못된 대상의 것**이면 판정은 근거를 갖춘 채로 틀립니다.

---

## 문제

sandbox 네임스페이스의 워크로드가 죽었습니다. 리포트를 열었더니 근거 로그에 **target 네임스페이스에서 돌던 Loki 자신의 ERROR 로그**가 섞여 있었습니다.

에이전트 정책은 로그 쿼리를 네임스페이스별로 여러 개 실행합니다. 결과가 한 번들로 합쳐지면서 어느 쿼리에서 왔는지가 사라졌습니다.

이건 [관련 문서](collection-contract.md)의 빈 목록 문제보다 조용합니다. 빈 목록은 최소한 비어 있기라도 합니다. 여기서는 **근거가 있고, 개수도 맞고, 심각도도 높습니다.** 다만 다른 사건의 것입니다.

## 판단

### 1. 무엇을 기준으로 귀속시키는가

Loki 정규화 payload의 stream 라벨을 씁니다. `k8s_namespace_name` 또는 `namespace`가 incident 리소스의 네임스페이스와 같은 stream만 남깁니다.

남는 stream이 없으면 entry 자체를 뺍니다. 빈 entry를 남기면 "로그를 봤는데 아무것도 없었다"로 읽힙니다.

### 2. 라벨이 없으면 어떻게 하는가

여기서 한 번 갈렸습니다. 라벨이 없는 stream은 귀속을 판단할 수 없습니다. 제외할 수도, 남길 수도 있습니다.

**남기는 쪽을 택했습니다.**

제외하면 근거가 소리 없이 줄어듭니다. 판정은 줄어든 줄 모르고 남은 것으로 결론을 냅니다. 남기면 무관한 로그가 섞일 수 있지만, 사람이 리포트를 보면 그건 눈에 띕니다. **모르는 것을 "아니다"로 처리하는 쪽이 더 위험하다고 봤습니다.**

같은 이유로 incident의 네임스페이스를 모르면 아예 필터하지 않습니다. 기준을 모르는 채로 거르면 무엇을 버렸는지도 모릅니다.

```python
def stream_matches_namespace(stream: dict, namespace: str) -> bool:
    labels = stream.get("stream")
    if not isinstance(labels, dict):
        return True  # 라벨 없음 → 귀속 불가, 보수적으로 유지
    for key in LOG_STREAM_NAMESPACE_LABELS:
        value = labels.get(key)
        if value is not None:
            return str(value) == namespace
    return True
```

### 3. 거르는 것만으로는 부족했습니다

stream을 걸러도 entry에는 **필터 전에 계산된 집계**가 그대로 남아 있었습니다. `line_count`, `pattern_counts`, `severity_counts`, `trace_ids`입니다.

로그 10줄만 남았는데 `line_count`가 400이면, 판정은 400줄을 근거로 판단합니다. **거른 것보다 나쁩니다.** 남은 것과 숫자가 어긋나면 어느 쪽도 믿을 수 없습니다.

그래서 남은 stream만으로 전부 다시 계산합니다.

| 값 | 처리 |
|---|---|
| `line_count` | 남은 stream의 values 길이 합 |
| `pattern_counts` · `severity_counts` | 남은 stream의 값만 합산 |
| `trace_ids` | 남은 stream에서만 수집 |
| `matched_entries` | 구조화 요약도 같은 범위로 다시 거름 |

### 4. 시나리오 검증에서는 기준을 올렸습니다

RCA 시나리오 테스트는 "이 장애를 넣으면 이 원인이 나오는가"를 확인합니다. 여기서 다른 Pod의 로그가 섞이면 **테스트가 통과해도 의미가 없습니다.**

그래서 RCA test metadata가 있으면 네임스페이스만이 아니라 **Pod 이름까지 일치해야** 채택합니다. 라벨이 없으면 그때는 제외합니다. 일반 incident의 보수적 규칙과 반대인데, 목적이 다르기 때문입니다.

| | 일반 incident | RCA 시나리오 테스트 |
|---|---|---|
| 기준 | 네임스페이스 | 네임스페이스 + Pod |
| 라벨 없는 stream | 유지 | 제외 |
| 틀렸을 때 결과 | 무관한 로그가 리포트에 섞임 | 검증 자체가 무효 |

## 검증

| 막으려는 사고 | 검증 |
|---|---|
| 다른 네임스페이스 로그가 근거에 섞임 | 두 네임스페이스 fixture → 하나만 남는지 |
| 필터 후 집계가 필터 전 값 | 거른 뒤 `line_count`가 남은 줄 수와 같은지 |
| 라벨 없는 stream이 조용히 사라짐 | 라벨 없는 fixture → 유지되는지 |
| 시나리오 테스트가 다른 Pod로 통과 | Pod 불일치 fixture → 0건 |

## 결과

- 장애 리포트의 근거 로그가 사건 대상의 것만 남습니다
- 근거 개수와 집계가 어긋나는 경로가 없어졌습니다
- 귀속을 판단할 수 없는 데이터는 **버리지 않고 남긴다**는 기준이 코드에 있습니다

→ [`src/services/ai/agent/pipeline/evidence_bundle.py`](../../src/services/ai/agent/pipeline/evidence_bundle.py)

## 이 작업이 증명하는 것

- 소비자가 무엇을 근거로 판단하는지 역추적해 **데이터의 귀속 범위를 정의**
- 필터와 집계의 정합성을 함께 다뤄야 한다는 이해
- 판단 불가 데이터를 **제외가 아니라 보존으로 처리**하는 기준과 그 근거
- 용도에 따라 같은 데이터에 다른 엄격도를 적용하는 판단

## 남은 것

거른 것은 리포트가 소비하는 근거 번들뿐입니다. **원본 `Evidence.logs`에는 전체 네임스페이스의 로그가 그대로 남습니다.**

제대로 고치려면 수집 시점에 incident별로 로그 쿼리를 나눠 실행해야 합니다. 그건 수집 파이프라인 변경이라 프로젝트 기간 안에 하지 못했고, **최소 수정이라는 것을 코드 docstring에 적어 뒀습니다.** 다음 사람이 이걸 완결된 해결로 오해하지 않도록 하는 편이 낫다고 봤습니다.
