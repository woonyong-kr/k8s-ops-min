# Kyro — 운영 데이터 수집·정규화와 메타데이터 카탈로그 정합성 검증

쿠버네티스에 익숙하지 않은 사용자가 GitOps 기반으로 장애를 스스로 복구할 수 있게 돕는 서비스입니다. 장애가 나면 운영 데이터를 모아 규칙으로 원인을 판정하고, 수정안을 Draft PR로 올린 뒤, 실제로 복구됐는지 확인합니다.

저는 이 서비스가 쓰는 운영 데이터를 맡았습니다. 수집과 정규화 계약을 만들고, 이후 메타데이터 카탈로그와 배치 파이프라인, 정합성 검사, 조회 API를 설계·구현해 등록한 스키마와 실제 데이터가 어긋나는지 검증하는 계층으로 확장하고 있습니다.

원인 판정과 복구 제안, 프론트엔드는 팀원이 맡았습니다. 제품 아키텍처도 팀 설계입니다.

**위쪽은 장애가 나면 도는 실시간 경로**입니다. 네 소스는 응답 형식도 시간 기준도 실패하는 방식도 다릅니다. 하나로 모으면서 각 데이터를 어디까지 믿어도 되는지 함께 넘기는 것이 제 일이었습니다. 원인 판정은 제가 준 데이터로 돌아가기 때문에, 절반만 왔다는 사실을 알리지 않으면 판정도 절반짜리 근거로 결론을 냅니다.

**아래쪽은 하루 한 번 도는 배치 경로**입니다. 실시간 경로는 수집하는 순간의 완전성만 봅니다. 수집이 성공한 뒤에 데이터가 어긋나는 것은 아무도 보지 않고 있었습니다.

이 저장소는 팀 저장소(`[팀 저장소 링크]`)의 사본입니다. 프론트엔드·GitOps 상태·배포 차트를 포함한 전체 코드가 그대로 들어 있고, 제 담당 범위는 위 그림과 아래 각 항목의 `개인`·`팀` 표시를 따릅니다.

### 1. 데이터 품질 검사 SQL
`SQL` `PostgreSQL` — 개인

**목적** — 수집이 성공한 뒤에 데이터가 조용히 어긋나는 것을, 그 데이터를 쓴 결과가 나가기 전에 잡으려고 만들었습니다.

배치가 오류 없이 끝나도 원천의 필드 타입이 바뀌거나, 새 데이터가 하나도 없거나, 더는 수집되지 않는 자산이 목록에만 남을 수 있습니다. 실행이 실패하지 않으니 알림이 울리지 않습니다. 통과 결과까지 저장해 **검사를 안 한 것과 검사해서 통과한 것을 구분**합니다.

**결과** — 실행 실패 없이 생기는 어긋남 6종을 검출합니다. 인덱스 조합은 측정으로 정했습니다. 빼면 424.5ms, 넣으면 150.0ms입니다(관측 60만 행).

→ [검사 SQL 열 개](docs/portfolio/06-sql-quality-checks.md) · 확인 `make catalog-sql`

### 2. 메타데이터 테이블 설계
`데이터 모델링` `스키마 이력` — 개인

**목적** — 등록한 계약과 실제 데이터를 **사람이 아니라 기계가 대조**할 수 있게 하려고 만들었습니다.

"이 자산에는 이런 필드가 있다"를 자유 텍스트로 적어 두면 아무것도 못 잡습니다. 필드 계약을 행으로 저장해야 대조가 됩니다. 그리고 계약을 한 테이블에 두고 덮어쓰면 적재가 이전 세대를 지워서 **변경을 판정할 근거가 사라집니다.** 관측 이력을 따로 쌓습니다.

**결과** — 버전을 올리지 않은 스키마 변경까지 검출됩니다.

→ [메타데이터 카탈로그](docs/portfolio/04-metadata-catalog.md) · 확인 `make demo-drift`

### 3. Airflow 배치
`Airflow` `멱등 재실행` — 개인

**목적** — 한 번의 수집만으로는 판정할 수 없는 검사를, 소스 하나가 실패해도 나머지는 살려 가며 돌리려고 만들었습니다.

실행 단위를 DAG 하나에 행 하나로 두면 소스가 넷인데 **어느 소스가 실패했는지 적을 자리가 없습니다.** 단위를 둘로 나눴습니다. 그리고 `trigger_rule` 이름에 조건을 맡기지 않고 task 본문에서 직접 확인합니다. 과거 날짜는 원천을 다시 조회하지 않고 보관본에서 재생합니다.

**결과** — 소스 1개 실패 시 나머지 3개 적재 + `PARTIAL` 기록. 재수집 대상 4개 → 1개. 같은 날짜 5회 재실행에 행 수 불변.

→ [배치 설계](docs/portfolio/05-airflow-pipeline.md) · [검사는 어디서 돌아야 하는가](docs/portfolio/15-where-checks-run.md) · 확인 `make demo-fail-source`

### 4. 카탈로그 조회 API와 MCP 서버
`FastAPI` `MCP 서버` — 개인

**목적** — 카탈로그를 사람과 모델이 함께 조회하는데, **모델이 부분 데이터를 전부로 오해하지 않게** 하려고 만들었습니다.

목록이 상한에 걸려 잘리면 사람은 다음 페이지를 누르지만 모델은 잘린 줄 모르고 "이슈가 3건뿐"이라고 답합니다. 절단 사실과 원본 개수, 다음 커서를 함께 보냅니다. 모든 응답에 마지막 배치 실행 상태를 붙여, `PARTIAL`이면 **이 조회 결과 자체가 부분 데이터**임을 알립니다.

**결과** — 응답 상한 50건 / 64KB. 경계 테스트 9종.

→ [조회 API와 MCP](docs/portfolio/07-catalog-api-mcp.md) · 확인 `make catalog-mcp`

### 5. 수집 상태와 사유 표시
`Python` `응답 계약 설계` — 팀

**목적** — 원인 판정이 **불완전한 근거로 결론 내리지 않게** 하려고 만들었습니다.

네 원천은 응답 형식도 시간 개념도 실패 방식도 다릅니다. 그리고 수집이 빈 결과로 끝나는 경우가 다섯 가지인데 전부 `[]`로 같았습니다. 저장소는 그걸 삭제로 읽었습니다. 실패 시 예외를 던지는 안도 검토했는데, 그러면 소스 하나만 죽어도 화면 전체가 빕니다. **부분 성공을 성공으로 다루되 어디까지 성공인지를 함께 넘기는 쪽**을 택했습니다.

**결과** — `completed`·`partial`·`unavailable` 세 상태와 사유 코드. 삭제 판정은 `completed`일 때만.

→ [수집 완전성 계약](docs/portfolio/01-collection-contract.md)

### 6. 로그 범위 필터
`로그 귀속` `집계 재계산` — 팀

**목적** — 원인 판정이 **다른 사건의 로그를 근거로 쓰지 못하게** 하려고 만들었습니다.

로그를 네임스페이스별로 나눠 질의하는데 결과를 합치면서 출처가 사라졌습니다. sandbox 워크로드 장애 리포트에 target 네임스페이스 Loki 자신의 ERROR가 근거로 들어갔습니다. 빈 목록보다 조용합니다. 근거가 있고 개수도 맞습니다. 라벨이 없어 귀속을 판단할 수 없는 스트림은 **제외하지 않고 남깁니다.** 제외하면 근거가 조용히 줄고 판정은 줄어든 줄 모릅니다.

**결과** — 근거 로그 1,180줄 → 240줄(fixture 기준). 거른 뒤 집계를 다시 계산해 남은 줄 수와 숫자가 어긋나지 않습니다.

→ [근거의 귀속 범위](docs/portfolio/11-evidence-scope.md)

### 7. ConfigMap·Secret 참조 조회 API
`FastAPI` `허용 목록 투영` — 팀

**목적** — 설정 장애를 조사할 수 있게 하되 **비밀키 값은 응답에 담기지 않게** 하려고 만들었습니다.

원문을 반환하면 값이 함께 나갑니다. 그래서 참조 관계만 투영했습니다. 문제는 검증이었습니다. 지울 필드를 열거하는 방식은 **제가 아는 자리만** 검사합니다. 원본 모든 문자열에 고유 토큰을 심고 허용 경로 밖에서 하나라도 나오면 실패시키는 방식으로 바꿨습니다.

**결과** — 통과하던 테스트 상태에서 `metadata.annotations`의 `last-applied-configuration` 안에 평문 환경변수가 남아 있는 경로를 검출했습니다. 이후 projection을 지울 필드 열거에서 채울 필드 열거로 재설계했습니다. 경계 조건 16종.

→ [설정 참조 조회 API](docs/portfolio/03-config-reference-api.md)

### 8. 응답 크기 제한 모듈
`수집 한도` `provider 공통화` — 팀

**목적** — 응답을 잘라야 하는 상황에서 **어느 그룹이 얼마나 빠졌는지 받는 쪽이 알 수 있게** 하려고 만들었습니다.

자르지 않으면 전송이 실패하고, 앞에서부터 자르면 특정 namespace가 통째로 빠집니다. 받는 쪽은 그게 전부인 줄 압니다. 그룹별로 예산을 나눠 자르고 개수와 바이트를 함께 제한하며, 원본 개수와 잘림 사유를 같이 보냅니다. provider 세 곳에 같은 로직을 넣다가 네 번째에서 멈추고 공통 모듈로 뽑았습니다.

**결과** — 네 곳 → 한 모듈. 이후 작업 순서가 `공통 모듈 수정 → 테스트로 고정 → 적용`으로 바뀌었습니다.

→ [수집 한도 설계](docs/portfolio/02-collection-limits.md)

### 9. API 상한값 상수
`상수 단일 출처` — 팀

**목적** — 라우터와 클라이언트가 **서로 다른 경계값을 갖는 상황을 없애려고** 만들었습니다.

목록 상한·문자열 길이·사유 코드 개수를 각자 들고 있으면 한쪽만 고쳐도 아무도 모릅니다. 클라이언트가 200을 기대하는데 서버가 100으로 줄이면 그냥 조용히 잘립니다.

**결과** — 전 도메인 경계값을 [91줄 한 파일](src/packages/contracts/gateway/limits.py)로 통합했습니다(단독 작성). 개선 수치는 없는 구조 결정입니다.

### 10. 안 쓰기로 한 도구 정리
`기술 검토` — 개인

**목적** — 규모에 맞지 않는 도구를 들여서 운영 비용이 이득을 넘는 상황을 피하려고 정리했습니다.

외부 데이터 카탈로그 도구를 검토했지만 자산이 6종이고 소유자가 한 팀인 규모에서는 도입 비용이 더 컸습니다. 자연어를 SQL로 바꾸는 기능도 뺐습니다. **생성된 질의가 맞는지 검증할 방법이 없기 때문**입니다. 대신 답은 결정론적 질의가 만들고 모델은 질문을 도구로 옮기기만 하도록 했습니다.

**결과** — 검토한 대안과 배제 사유를 남겨, 다음 사람이 같은 판단을 다시 하지 않아도 됩니다.

→ [기술 리서치](docs/portfolio/08-tech-research.md)

## 확인하기

AWS 계정도 실제 클러스터도 필요 없습니다. Docker 만 있으면 됩니다.

**1단계 — 카탈로그** (Docker 필요, 약 3분)

```bash
make catalog-up        # PostgreSQL · MinIO · Airflow 기동
make catalog-run       # 배치 1회 실행
make catalog-verify    # 검증 15항목      → 15/15 통과
make catalog-test      # 단위 테스트       → 15 passed
make catalog-bench     # 인덱스 전후 비교   → 424.5ms → 150.0ms
```

**2단계 — 고장 시연** (약 2분)

```bash
make demo-fail-source  # Loki 를 끊고 배치     → PARTIAL 기록, 나머지 3개 적재
make demo-drift        # 원천 필드 타입 변경   → 스키마 드리프트 검출
make demo-duplicate    # 같은 날짜 두 번 적재  → 중복 적재 후보 검출
```

정상 데이터로만 시험하면 무엇이든 통과한다고 답하는 검사도 통과합니다. 그래서 일부러 고장 내는 명령을 함께 뒀습니다.

- 실제로 반복 사용한 사용자가 없습니다. 시연에 성공한 것과 쓰인 것은 다릅니다
- 카탈로그가 다루는 것은 이 프로젝트가 만드는 운영 데이터 6종입니다. 외부 업무 시스템 연동은 조사까지만 했습니다
- 배치와 카탈로그는 프로젝트 종료 후 개인 작업이며 AI 코딩 도구를 함께 썼습니다. 설계 판단과 검증은 직접 했고, 각 선택의 대안과 배제 사유를 문서에 남겼습니다
- 팀 저장소는 이력 정리를 여러 차례 거쳤습니다. 커밋 수는 기여의 근거가 아닙니다. 파일 단위 blame 과 코드로 확인하는 편이 정확합니다
